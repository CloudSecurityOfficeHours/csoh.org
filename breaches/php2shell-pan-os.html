PHP2Shell / PAN-OS Firewalls 2026

Step-by-step kill chain mapped to MITRE ATT&CK Cloud, sourced from official post-mortems and primary technical analyses.

October 2026 Critical PHP / PAN-OS

PHP2Shell / PAN-OS - A Bug Class From 2004 → An Embargo That Broke in Stages → Mass Scanning That Mostly Failed → Exploits Tuned Per Firmware Version → 25 Palo Alto Systems Rooted → Active Directory

PHP2Shell covers two memory-safety flaws in core PHP, CVE-2026-109618 and CVE-2026-109619, each scored 9.2 under CVSS 4.0, with affected code reaching back to PHP 5.4. The bug class dates to 2004, and a 2024 audit saw the problem without proving it could be exploited. Calif reported it to PHP on August 11, and OpenAI and Wiz followed with the same root cause or further attack vectors. The CVE IDs leaked on October 20, the embargo broke in stages, and governments across Europe pulled services offline as a precaution. Amazon reported the earliest known attempt, against a honeypot, dated October 17. Mass exploitation then ran into a practical limit: a working exploit has to fit the target's build, configuration and worker model. As of October 28 Wordfence knew of no WordPress site compromised this way, despite more than 77,000 related requests. Tenable points to the exception: appliances, where many devices share one build, so one calibrated exploit can reach them. On October 23 and 24 an operator used a private exploit tuned to specific PAN-OS versions, chained it with the Fragnesia Linux kernel flaw, and took root on Palo Alto Networks firewalls with internet-exposed management interfaces. Dream recovered the toolkit and reports 24 of 240 targeted firewalls rooted plus a 25th system, a firewall management server in a US government-affiliated network, from which the operator reached Active Directory. Unit 42 says it independently verified the tooling and results. This page runs in order: the flaws and the disclosure, the scanning and first working exploits, the PAN-OS kill chain, then what changed on cloud platforms and what is still unresolved.

🕰️ Background: A Bug Class From 2004
01
The bug class dates to 2004, and a 2024 audit saw the problem without proving it could be exploited

Calif's write-up starts with Stefan Esser's 2004 memory-limit remote code execution bug. A PHP bug report filed in November 2019 described out-of-memory conditions from long multipart variables. In 2024 an audit by OSTIF and Quarkslab turned up a related issue, and a PHP core developer fixing one of its findings saw the first signs of the problem behind CVE-2026-109618. The PHP Foundation says a potential exploit was theorized then, with no concrete vectors found, and Calif says the lack of proven exploitation is why it stayed unfixed.

The 2026 work began from that history. Calif joined OpenAI's Patch the Planet initiative on July 30, found its first out-of-memory trigger on August 1, reported to PHP on August 11, and saw PHP confirm its proof of concept on August 15. Calif says an LLM assistant helped search for memory-limit bypasses, an audit agent spotted the ordering bug in PHP's hash table code, and a model generalized that pattern into the session upload-progress finding. Its author argues the models needed steering from someone who knew the target's vulnerability history.

OpenAI independently reported the same root cause, and further attack vectors followed from Wiz on August 24 and OpenAI on September 18. Wiz says it used Gemini 4 Argon, GPT-5.6 Sol and its own Atlas tooling. Calif reports pre-authentication code execution against specific versions of WordPress, Drupal, Joomla, MediaWiki, Magento and Nextcloud. Fixes shipped about ten weeks after the first report.

🧬 Background: What the Flaws Do
02
Both CVEs come from what PHP leaves behind when a request is interrupted, and the risk depends on how PHP is deployed

CVE-2026-109618 comes from PHP's use of longjmp() to escape on an out-of-memory error. If the allocation fails while request memory is only partly set up, request shutdown can read or branch on invalid state. PHP's advisory lists several ways to force that failure with an ordinary request: a multipart request with no usable content length gets past post_max_size, a part can carry unlimited headers, and empty file fields with nested names multiply allocations without counting toward max_file_uploads.

CVE-2026-109619 is stale state: a worker keeps global pointers into memory owned by a previous request. Exploiting it takes a producer request that leaves the state behind and a consumer request that reads it before initialization, and both must reach the same worker. Session upload progress can play both roles, is on by default, and does not need the application to call session_start(). Wiz says the flaws can also disclose live worker memory through an oversized PHPSESSID cookie, with no code execution at all, and that this memory may hold passwords, tokens and API keys from other requests.

Deployment decides a great deal. PHP rates Apache mod_php highest because shutdown runs even when startup fails, so the attack lands before any application code runs, and it validated full code execution there with default limits. PHP-FPM exits the child on a startup failure, which limits exposure. The official 9.2 score reflects high attack complexity and attack requirements. The 10.0 that circulated with the leak was wrong.

Apache mod_php: full code execution validated with default limits; PHP's highest risk
PHP-FPM: no complete exploit shown for 109618; upload-progress path validated with a suitable application operation
FrankenPHP: likely susceptible by source analysis, per PHP
LiteSpeed (LSAPI): application-specific exploits likely, not validated
Fixed releases: 8.5.12, 8.4.27, 8.3.36, 8.2.35
End of life: source backports for 7.4, 8.0 and 8.1; no PHP project fix for 5.4 to 7.3

📣 Disclosure: An Embargo That Broke in Stages
03
The CVE IDs leaked, PHP moved its release up a day, and the embargo kept breaking

Tags and tarballs for the fixed releases were built on October 19, with publication planned for 14:00 UTC on October 22. At about 15:00 UTC on October 20 the two CVE IDs began circulating online, with a wrong release time and the wrong CVSS score, and PHP says no technical details leaked. PHP moved the release to 14:00 UTC on October 21. That left about 23 hours with a public warning and no installable patch.

More breaks followed. Around 20:00 UTC on October 20 Calif mistakenly published a video of its proof of concept, and copies spread after it was deleted. The PHP Foundation says the video helped speed up other proofs of concept, and that mitigation advice given to critical infrastructure providers from about 23:00 UTC may also have leaked. Amazon puts the earliest proofs of concept at around 02:00 UTC on October 21. By the Foundation's account, Chainguard published images containing the fix at 07:41 UTC, more than six hours before the coordinated release, and it calls that a unilateral break of the embargo.

One attempt predates all of this. Amazon found it in its MadPot honeypots dated October 17, from an address tied to a commercial anonymization network. Amazon says it is unclear whether these early attempts would have succeeded on real systems, or how the actor got exploit details ahead of disclosure.

🏛️ Reaction: Patch or Go Offline
04
Agencies told organizations to patch or go offline, and many pulled services before any confirmed exploitation

CISA told organizations that could not update immediately, or that still ran PHP 8.1 or earlier, to take PHP systems offline until patched. The NSA said much the same on October 21 and the FBI on October 23, and the FBI, like CISA, told organizations to look for vendor products that bundle PHP. The UK's NCSC warned against limiting discovery to outdated versions.

Governments across Europe went further on October 21. eBuilder Security's round-up of official statements lists Germany's federal IT provider ITZBund, French prefecture websites, Belgian foreign ministry sites, the Czech government and Finland's state IT centre Valtori. The Dutch list was the longest: NCSC-NL took down its own site, and the Port of Rotterdam, Overheid.nl, the KNVB and many hospitals followed. SecurityWeek reported 32 UK services unavailable and four partly unavailable, largely as a precaution. As of October 22 that round-up described the shutdowns reported so far as precautionary, with no government reporting a breach. Belgium's foreign ministry acted after reports of attacks, though its cybersecurity centre had recorded none against Belgian sites.

Assessments then cooled. By October 23 NCSC-NL said exploitation was complex and that large-scale exploitation was less likely than it had estimated, while still telling organizations to patch at once. CISA added both CVEs to its Known Exploited Vulnerabilities catalog on October 26 with a federal deadline of October 29. The Register notes the listing does not say how many production systems were breached.

📡 Mass Scanning: Loud and Mostly Unsuccessful
05
Attempts ran into the millions, and little of what looked like exploitation is shown to have worked

SecurityWeek reported that attempts ran into the millions. Delft University's Threat Intelligence Lab tracked more than 50,000 exploitation requests from over 600 addresses across 70 countries, and 171 of those addresses went beyond probing to send exploit code or droppers. Wordfence recorded over 77,000 related requests from more than 2,000 addresses and, as of October 28, knew of no compromised WordPress site. Cato Networks said about 96% of the attacks it blocked targeted CVE-2026-109618.

Much of that traffic failed on the targets it hit, and success depended on the target. As of October 27 Wiz's telemetry showed no successful end-to-end exploitation: two variants of an open-source kit hit request-size limits or failed to obtain memory addresses in the attempts it captured, even though two of those same source addresses succeeded against the honeypots in the next step. A PHP2Shell-branded tool relied on session poisoning and a separate local file inclusion endpoint, exploiting neither CVE. Arctic Wolf saw similar requests that appeared to reuse older session-poisoning and deserialization tricks.

SOCRadar found an operator's open server holding a lab-tested exploit for PHP 8.4.26 under mod_php, with a calibration profile for the official Apache container image. It depended on a debug-style setup: visible errors, a very low memory limit and a single Apache worker. The operator screened about 20 live sites and probed 11 closely, and none met the preconditions. Hunt.io counted 123 servers targeted from that host with none exploited. Sophos saw a blocked attempt to install Potassium, which it believes is a Mirai variant, and Hunt.io separately attributes the PHP2Shell traffic it observed to a Mirai-style botnet active since at least May.

Attribution is thin. CYFIRMA reports a suspected North Korean effort, based on Korean-language operator chat, targeting pattern and past Lazarus tradecraft, with 216 hosts on a captured target list and 581 claimed by the operators. It says claims of web-shell deployment are self-reported and not confirmed per host. Its fourth version raised confidence in the Lazarus link from moderate to high without explanation, and without reporting the infrastructure overlap or confirmed compromises its first version said would raise it. That first version cautioned that language alone could reflect a Korean-speaking criminal crew. CISA's alert names no actor.

🎯 Working Exploits: Favorable Targets First
06
Working exploits appeared within days, and each needed the right conditions or tuning

The first solid proof came from honeypots. On October 24 Adel Karimi's sensors recorded 35 shells across three targets running PHP 8.4.26 under single-worker Apache mod_php, from two source addresses. The report ties each shell to an execution-stage request and a /bin/sh process started by an Apache worker, with memory leaks guiding the chain to each target's randomized layout. The activity fits CVE-2026-109618, attackers tried to fetch more with PHP, curl and wget, and no second stage was downloaded. Karimi says this deliberately favorable profile does not measure reliability on other worker counts, builds or applications. GreyNoise later said it had seen at least six successful exploitations.

James Pavur then tested the hard version of the question. His Steal My Bitcoin challenge, launched on October 24, offered Bitcoin for code execution on a vulnerable server behind Nginx with a 1 MB request limit. After Pavur apparently added a PHP endpoint around 13:00 UTC on October 25, UK pentester Jaydip Modhwadia won at 15:47 UTC. By his account, his Python script needed at most 20 HTTP requests, and it got past ASLR, which early reports had treated as a major barrier. Alon Gal of Hudson Rock said this shows PHP2Shell can be weaponized against a live target, and cautioned that it was a sophisticated, target-specific exploit and no sign that autonomous AI agents could compromise PHP servers at scale.

Other teams reached the same place. Tenable says Trail of Bits reported exploits against PHP 8.2 through 8.5, with demo shells on MediaWiki, Symfony, Laravel and phpBB. VulnCheck built one for x86-64 with ASLR on and error display off, available only to its customers. Tenable's own week of testing found exploits had to be fitted to each target, and five sites it left exposed had not been compromised as of October 29, though four of them came down on October 24. Researchers still disagree on how much of a barrier that is, and Wiz expects it to shrink over time.

🔍 The PAN-OS Chain, Reconnaissance: 19,000 Firewalls Narrowed to 240
07
FOFA listed about 19,000 internet-facing PAN-OS firewalls, and a country and version filter cut that to 240
T1595.002 - Vulnerability Scanning

The target lists Dream recovered show a plain funnel. The FOFA internet search platform supplied about 19,000 internet-facing PAN-OS firewalls. A fingerprinting scanner running 200 concurrent threads got responses from about 5,000. The operator then kept devices in the United States, Japan, Taiwan and South Korea on the 12.1 and 12.2 branches, which left 240 targets.

Every one of those devices was reachable because its management interface had been exposed. Palo Alto Networks says the interface is not internet-exposed by default and puts the affected share at about 0.02% of its installed base. Dream reads the four countries as a sign of Chinese state-aligned targeting, and that reading is Dream's interpretation.

Source: FOFA, about 19,000 internet-facing PAN-OS firewalls
Fingerprinted: about 5,000 responded, 200 concurrent threads
Filter: US, Japan, Taiwan, South Korea; PAN-OS 12.1 and 12.2
Result: 240 targets
Palo Alto's figure: about 0.02% of its installed base internet-facing and affected

🧰 Resource Development: An Exploit Calibrated to the Firmware
08
The exploit shipped with a profile for each PAN-OS version, which is what made one tool reusable
T1587.004 - Develop Capabilities: Exploits

Public proofs of concept were a poor guide to this bug. PHP's security team said it identified no functional exploit at the time of release, and Tenable spent a week showing why: the memory layout an exploit relies on shifts with the PHP build, server API, extensions and runtime settings. Five deliberately vulnerable sites Tenable exposed to the internet had not been compromised as of October 29, though four of them came down on October 24, and its own working exploit needed tuning to one setup.

An appliance removes that obstacle. Dream recovered 11 JSON version profiles: two for the 11.1 branch on PHP 7.4.33 and nine for 12.1 and 12.2 on PHP 8.0.30. One of the nine had been calibrated against a running virtual machine, and the rest used offsets derived from the binary without live testing. Tenable's advice for appliances is to go by the vendor's build, since PHP version numbers do not apply.

The AI angle is narrower than the headlines. Dream found Claude Code installed in the attack infrastructure, the aiscan platform configured with DeepSeek and Kimi, and scripts whose structure suggests AI-assisted development. It also says it has no direct evidence that AI tools wrote the exploit or the post-exploitation scripts, and that the operation does not appear fully autonomous.

Profiles: 11 JSON files, one per tested PAN-OS version
11.1 branch: PHP 7.4.33, 2 provisional profiles
12.1 and 12.2: PHP 8.0.30, 1 calibrated and 8 provisional
Why it worked: every device on a release shares one build, so one calibration carries over

⚡ Initial Access: No Credentials Needed
09
A staged exploit against PHP's upload-progress handling gave code execution on the management web server
T1190 - Exploit Public-Facing Application

The flaws work here the way the background steps describe. PHP processes the request before any application code runs, so the management interface's own login offers no protection.

Dream describes a custom build aimed at PHP's session.upload_progress mechanism on the PAN-OS management web server: memory exhaustion, an information leak, a stale-reference setup, then a final request that yields code execution as the low-privileged nobody user. Palo Alto's advisory scopes the issue to the management web interface, meaning the HTTPS web UI and XML API, and says GlobalProtect and Captive Portal are not impacted.

Flaws: CVE-2026-109618 (out-of-memory corruption), CVE-2026-109619 (stale global state), both CVSS 4.0 9.2
Target: PAN-OS management web interface, PHP 8.0.30 on 12.1 and 12.2
Stages: memory exhaustion, information leak, stale-reference setup, code execution
Result: code execution as nobody, with no credentials

⬆️ Privilege Escalation: Fragnesia
10
A Linux kernel flaw overwrote the PAM configuration, so su root needed no password
T1068 - Exploitation for Privilege Escalation

A shell as nobody on a firewall gets an attacker very little, so the operator brought a second exploit. CVE-2026-46300, known as Fragnesia, is a privilege-escalation flaw in the kernel's XFRM ESP-in-TCP code. Dream says it was used to overwrite /etc/pam.d/su to accept all authentication, after which su root succeeded without a password.

Dream says the final stage's single HTTP request carried both exploits, with no credentials, and that the chain from an unauthenticated HTTPS connection to a persistent root webshell takes under 15 minutes. A batch runner worked five targets at a time with a 30-minute timeout on each, and 24 of the 240 were rooted. CISA added Fragnesia to its Known Exploited Vulnerabilities catalog on October 28.

Flaw: CVE-2026-46300 (Fragnesia), XFRM ESP-in-TCP
Method: overwrite /etc/pam.d/su so su root accepts anything
Automation: batch runner, 5 targets at a time, 1,800-second timeout
Yield: 24 of 240 firewalls rooted

🔐 Persistence: Park Most, Work a Few
11
Most victims received a 103-byte webshell and were left alone
T1505.003 - Server Software Component: Web Shell

The operator's next move was triage. A 103-byte PHP root webshell went to /unauth/php/change_password.php, confirmed by running id. For 22 of the 24 rooted firewalls that was all: no tunnel and no tools. Dream says they remain parked with active webshells, and that the operator could return at any time.

The first firewall in the US government-affiliated network fell at 18:14 UTC on October 23 during the batch run, crashed shortly afterwards and never came back. Hours earlier, SecurityWeek's round-up had reported no confirmed compromise from any vendor. A second firewall, whose certificate data tied it to the same organization, had only timed out in the batch. Once the first firewall's configuration suggested a government affiliation, the operator ran a dedicated campaign against the second.

Prioritized: 2 firewalls in one US government-affiliated network

🔀 Command and Control: The Firewall as a Bridge
12
An eight-port reverse SSH tunnel put the internal network within the operator's reach
T1572 - Protocol Tunneling

The second firewall was exploited at 10:09 UTC on October 24 and got the full treatment. Dream describes an eight-port reverse SSH tunnel to operator infrastructure, reaching domain controllers over LDAP, LDAPS and RDP, along with the firewall management server, GlobalProtect infrastructure and a SOCKS5 proxy.

A systemd service and an rc.local hook launched scripts from /usr/local/lib/.panops/, so the access survived a reboot. iox, a Chinese-developed tunneling utility, was among the recovered tools. Dream says the tunnel and webshells are likely still active and could not confirm it.

Boot survival: systemd service plus rc.local hook
Tooling: iox tunneling utility, about 40 post-exploitation scripts

🔑 Credential Access: What a Firewall Holds
13
Root decrypted the LDAP service account and exposed the private keys and SAML settings on the device
T1552.001 - Credentials in Files

A firewall that authenticates VPN users keeps a directory credential on the device. With root the operator had the master key, decrypted the LDAP service account password from the configuration, and hardcoded it into later scripts. Private keys for HA replication, SSL/TLS and device authentication came off the filesystem, along with the full network topology.

The haul also included a SAML IdP configuration with validate-idp-certificate: no, which Dream lists among weak security settings and does not tie to a specific device. None of this depended on PHP. A perimeter device carries the organization's trust relationships, and a rooted one hands them over.

Taken: private keys for HA replication, SSL/TLS and device authentication
Also taken: complete network topology
Weakness found: SAML IdP config with validate-idp-certificate: no

14
The same chain, sent through the tunnel, took the server that manages all of the organization's firewalls
T1210 - Exploitation of Remote Services

At 11:35 UTC on October 24, under 90 minutes after the second firewall, the operator exploited a central firewall management server through the tunnel. That brought the total to 25. Dream says this server manages all of the organization's firewalls and held LDAP connectivity to Active Directory because it authenticates VPN users. Dream does not name the product.

🔍 Discovery: Directory Enumeration, Then Unknowns
15
LDAP enumeration of the directory is confirmed, and the outcome of the spray, backdoor accounts and SAML theft is unknown
T1087.002 - Account Discovery: Domain Account

Dream confirms full enumeration of users and groups over LDAP. The recovered scripts went further: a password spray against all users on a domain with lockoutThreshold=0, backdoor user accounts in every OU, machine accounts through MachineAccountQuota, ACL chain analysis, SAML signing key extraction from Keycloak configuration, and probing Keycloak for an authentication bypass.

The results of those runs were not among the artifacts Dream recovered, so treat every item in that list as attempted. Dream also lists the full extent of the compromise in this environment as unknown.

☁️ Cloud Platforms: Who Owns the Patch
16
On cloud platforms, whoever owns the runtime owns the patch, and the line moves from service to service

The three big clouds drew the line in different places, and a managed service label does not settle it. On AWS, Amazon WorkMail was patched for customers. Elastic Beanstalk has updated platforms for PHP 8.2 through 8.5, which Managed Platform Updates apply at the next maintenance window, and everyone else must update the platform version. Lambda has no managed PHP runtime, so custom runtimes, container images and Bref users must redeploy. AWS cannot update running Lightsail instances in place, and tells customers to create new instances from updated blueprints and migrate. Amazon EMR on EC2 is affected when clusters include Ganglia on releases up to 6.15.0, and CodeBuild's curated images carry the fix from October 30, which matters for builds that start a PHP server and use pinned or custom images.

On Azure, App Service on Linux, Static Web Apps and Logic Apps run updated built-in runtimes, and Linux apps on the Extended channel should move to Standard or Latest. The built-in PHP runtimes on App Service for Windows are end of life, so Microsoft says to move to Linux or bring a supported runtime. VMs and scale sets that use automatic guest patching or automatic OS image upgrades get fixes within their maintenance windows, on Linux distributions such as Azure Linux and Ubuntu. Microsoft updates PHP preinstalled on its hosted Azure DevOps images, image by image, while self-hosted agents and job containers are yours.

On Google Cloud, App Engine standard on PHP 8.2 or later is patched automatically, and older runtimes must upgrade. App Engine flexible needs a redeploy. Cloud Run and Cloud Run functions are patched automatically only with automatic base image updates enabled. GKE is entirely on the customer. PHP 5.5, 7.2, 7.3, 7.4 and 8.1 runtimes will not be patched.

Two rules hold everywhere. Custom images and containers carry their own PHP, so updating the host does nothing for them. And a package update on disk leaves the vulnerable code running: Google notes that libphp.so and php-fpm stay resident in workers until they restart. Wiz's October 27 post says it had not seen successful end-to-end exploitation in its own telemetry, and that is a statement about its data at the time. A compromised worker runs with whatever identity the platform gave it, which is the reason to scope that identity tightly.

Provider patched: Amazon WorkMail; Static Web Apps and Logic Apps built-in runtimes; App Engine standard 8.2+
Provider patched, conditions apply: Elastic Beanstalk with Managed Platform Updates; App Service on Linux on a supported version and channel; Cloud Run with automatic base image updates
You redeploy: Lambda custom runtimes, Lightsail, App Engine flexible, GKE, EKS and ECS images, custom containers

📦 Hidden PHP: Products That Bundle It
17
Warnings about bundled PHP held up, because vendors kept finding it in their own products

PAN-OS was the sharpest case and not the only one. Oracle's alert lists eight Communications products, Oracle Secure Backup and Solaris 11, and it was still adding products on October 26. Sophos took its legacy MyUTM licensing portal offline on October 21 and says it found no evidence of exploitation to date. AWS's own list includes Ganglia on EMR and WorkMail. NCSC-NL warned that PHP is embedded in appliances and management interfaces that administrators may not be able to update themselves.

Palo Alto's advisory also shows how a vendor scopes this. It lists the affected PAN-OS branches and fixed hotfixes, lists its cloud services as not currently affected, and says Cortex XCORE and WildFire Cloud were impacted until patched on October 21 and 22. Qualys data from more than 10,000 customers shows the scale of the inventory problem: of 156 million PHP installations with a known version, 110 million ran end-of-life releases from 5.4 to 8.1.

🧾 The Record So Far: Exposure, Patching, Corrections
18
Exposure counts differ by more than 20 times, exposure fell quickly, and several early claims were withdrawn

Exposure figures depend on what is counted, and a version match does not prove exploitability. Silas Cutler roughly estimated 1.3 million potentially vulnerable hosts, Shodan showed about 1.9 million PHP hosts, VirusTotal about 5.1 million, Cortex Xpanse 22.6 million instances, Censys's dashboard about 30.3 million services on an affected version on October 29, per Tenable, and Bitsight nearly 37 million systems running PHP or related software.

Exposure fell quickly in the first week. Wiz says organizations with an exposed vulnerable instance fell by about 47.9%, though it cannot split that between patching, retirement and restricted access, and notes that changes in scan coverage can also move the numbers. Qualys counted only 199,000 instances patched in the first 12 hours. The PHP project published no fix for 5.4 through 7.3, so those installs need a vendor backport or an upgrade.

Several early claims did not hold. Sophos corrected a report of a successful Mirai-variant install to an attempt. Unit 42 retracted an October 23 update describing an attack on a European government agency, including stolen password hashes and an NTLM relay, because it could not tie the initial access to these CVEs. BankInfoSecurity notes that Sophos and Palo Alto Networks each reported working exploits and later retracted those claims.

The story is not finished. CVE-2026-115560 is a separate flaw that the October 21 releases do not fix. It affects applications that change session.serialize_handler to php at runtime with upload progress enabled, PHP calls exploitation unlikely in practice, and the fix is planned for a regular release. Datadog notes the counter-before-allocation pattern remains in PHP and expects more variants. PHP 8.4.27 and 8.5.12 also shipped a regression that can crash some SimpleXML applications, from an unrelated garbage collector fix.

🛡 How to Defend Against This Chain

Take management interfaces off the internet. Everything in the PAN-OS chain began at a management interface reachable from anywhere. Palo Alto's guidance is to remove internet access immediately and restrict the interface to trusted internal addresses or a jump box. Apply the same rule to every appliance you run, and alert when one becomes reachable.
Find every PHP, then patch the one serving requests. Inventory AMIs, container images, Kubernetes workloads, serverless functions, appliances and products that bundle PHP, and do not stop at old versions, as the NCSC warns. The fixed releases are 8.5.12, 8.4.27, 8.3.36 and 8.2.35, with source backports for 7.4, 8.0 and 8.1. The PHP project published no fix for 5.4 to 7.3, so those need a vendor backport or an upgrade, and PHP 8.2 itself reaches end of life on December 31, 2026. Compare the full package revision with your vendor's advisory, because backports do not always change the version. For appliances, follow the vendor's fixed build.
Know who patches each cloud runtime. Check each service against the provider's bulletin instead of assuming that managed means patched. Turn on Managed Platform Updates and automatic base image updates where you rely on them, redeploy everything built from a custom image, and move off App Service for Windows built-in PHP and any runtime on 8.1 or earlier.
Restart workers, and capture memory first if you see signs of probing. A package update on disk leaves vulnerable code running until PHP-FPM, Apache, FrankenPHP or LiteSpeed restarts. Google's guidance is to capture worker memory before patching or rebooting a server showing active probing or anomalous PHPSESSID cookies, because a restart destroys that evidence. During mass scanning almost every exposed host sees probes, so in practice reserve this for anomalous cookies or signs of compromise, isolate that host first, as the FBI advises, and do not let it hold up patching the rest.
Treat a WAF as time, and do not call it a fix. AWS WAF, Azure WAF, Cloud Armor and Cloudflare all shipped rules, and each vendor says they do not replace patching. Cloudflare says attackers mutated payloads to try to bypass its rules and that, for the related CVE-2026-115560, customers who changed session.upload_progress.name are not covered. Rules cover only traffic that passes through them, and rules in detection-only mode block nothing.
Treat interim settings as partial. PHP's advisories say no configuration fully mitigates these flaws. Set session.upload_progress.enabled=0 in php.ini or the pool configuration, not with ini_set() or .user.ini, and restart every worker. PHP advises leaving it off after patching if you do not use the feature, and it is also the interim answer to CVE-2026-115560. On PHP 8.5, also set fatal_error_backtraces=0. memory_limit=-1 removes the predictable limit, but an allocation failure can still reach the bug, so pair it with a container or cgroup limit as an availability boundary, check that nothing restores a finite limit, and put one back after patching. Avoid RLIMIT_AS and RLIMIT_DATA, which can cause the failure you are trying to prevent.
Look back further than the patch date. Begin no later than October 17, Amazon's earliest published sighting. Sophos recommends reviewing from August 1. Look for Set-Cookie: PHPSESSID values over 256 bytes, bursts of 50 to 150 OPTIONS * keep-alive connections, rapid interleaved 500 and 200 POST responses, POST requests containing PHP_SESSION_UPLOAD_PROGRESS, and sh, curl or wget spawned by a PHP worker. No single signal confirms exploitation. Memory disclosure may leave no shell at all, so rotate secrets that exposed workers handled.
Treat a rooted firewall as a directory compromise. On PAN-OS, hunt for /unauth/php/change_password.php and /usr/local/lib/.panops/. If you find either, assume the attacker holds the LDAP service account, the device's private keys and its configuration. Rotate those, reissue certificates, and review the directory for new users and machine accounts rather than stopping at the firewall.
Fix the directory settings this operator went looking for. A lockoutThreshold of zero makes spraying free, a default MachineAccountQuota lets ordinary accounts add machines, and SAML configuration that skips certificate validation weakens assertion checking. Each one helps turn a foothold on a firewall into a path to the domain. On Linux hosts you run yourself, patch the kernel too: Fragnesia, public since May, is what took this chain from a low-privileged worker to root.
