wfx-loot / WFX Phantom 2026

Step-by-step kill chain mapped to MITRE ATT&CK Cloud, sourced from official post-mortems and primary technical analyses.

November 2026 Critical GitHub Actions / AWS / Azure

wfx-loot / WFX Phantom - Tokens for 4,837 Compromised GitHub Accounts → Probe Pull Requests in 61,764 Repositories → Stealer Pushed, Run and Reverted → Runner Memory and Cloud Tokens Swept → Cloud Access Built to Outlive Rotation

Starting at about 12:45 UTC on November 10, 2026, someone holding GitHub credentials for thousands of accounts opened a pull request titled docs: dependency audit notes, from a branch named wfx-docs, in each repository it was testing. Aikido Security, which SafeDep says first reported the campaign, counts "4,837 compromised accounts opened probe pull requests in 61,764 repositories." In a smaller set of those repositories the operator then pushed a shell stealer of about 1,500 lines in one of four forms: steps added to an existing workflow, code appended to a shell script the repository already runs, a new workflow file on a throwaway branch, or a hidden script run by an npm postinstall hook. All but the new workflow went straight to the default branch. "The commits are authored as real users of the repository, with their noreply email and no signature," SafeDep says. Within at most a minute, by Aikido's account, the operator reverted the change and deleted the workflow run along with its logs. Where it ran, the stealer read the memory of the runner process that holds decrypted secrets, took every Actions secret and variable directly when it ran from a workflow file, swept credential files and AI tool keys, tried to exchange GitHub OIDC tokens for AWS, Google Cloud and Azure access, and sent the lot as one archive to a bare IP address on port 8080 and, from November 12, to a Telegram bot. The vendors name it differently: Aikido calls it wfx-loot, StepSecurity WFX Phantom, and SafeDep and Endor Labs wfx. The names refer to one campaign, and SafeDep explains the shared part: "The name wfx comes from the prefix the payload puts on its files, branches and cloud objects."

What this chain adds is cloud access that rotating GitHub secrets does not remove. The site already covers Megalodon, a May 2026 campaign that pushed workflows into thousands of repositories to sweep CI runners for credentials. wfx does that too, and then, where the cloud permissions it finds allow, it tries to leave access behind. In Azure it adds federated identity credentials named wfx-ci-<n> (StepSecurity) to app registrations, after which, in SafeDep's words, "Any workflow on the repository's main branch can then log in to Azure as that app, even after you rotate client secrets." In AWS, having assumed one role through GitHub OIDC and then a second, chained role, it sets the chained role's trust policy to "Principal": {"AWS": "*"}, "which opens the role to any AWS account" (Aikido), and it "lists IAM users and calls iam:CreateAccessKey for up to two of them" (GitGuardian). Each change succeeds only where the stolen session holds the permission for it. GitGuardian says the code "tries to rewrite the chained role's trust policy", and no source reports a rewritten role, a created key or a wfx-ci- credential found in a victim's cloud. The two clouds differ in a way that matters for clean-up, as the CSA note points out. The Azure credential works only for a workflow on one branch of that repository, the branch the payload names (main in SafeDep's samples), so taking away the hijacked account's write access also blunts it, though in the CSA's words it "grants renewed access to anyone who later regains write access to that repository." The open AWS role gives "immediate access that is independent of GitHub" (CSA). No source links wfx to Megalodon beyond similar techniques. Megalodon pushed from throwaway accounts under forged bot names; wfx commits as the real account, reverts its change and deletes the run, and reads the runner's memory.

How the operator got the tokens is unconfirmed, and the published counts measure different things. Endor Labs: "How the credentials were stolen has not been confirmed for the campaign as a whole." Three partial explanations are on record, and no source offers any of them as the root cause. Fly.io says tokens issued to its GitHub App leaked from .git/config files that some of its customers' apps served on the internet, and that "Fly.io's systems were not breached." The owner of one hit repository says the probe on it "was created with a leaked GitHub CLI OAuth token". And GitGuardian found that "431 of the accounts used in the wfx campaign, about 20%, were already compromised in the GhostAction wave", an earlier campaign it tracks. Aikido nonetheless assesses the two as "distinct campaigns likely carried out by different threat actors", and no actor is named. Repository counts run from 61,764 probed down to "at least 1,806" with indications that the payload ran; step 10 sets them side by side and says what each one counts.

Confirmed cases are few, partly because the evidence was deleted. At Nextcloud's nextcloud/docker repository the cleanup failed, and the surviving run shows that the stealer, appended to a script the repository runs, ran and, by StepSecurity's reading of the log, uploaded its archive. The owner of StringKe/kxen posted a notice on the probe pull request there saying that the attacker's workflow change read all Actions secrets and sent them to 18.143.168.96, and told maintainers to treat every secret as compromised; the notice names no run in kxen itself. At WebdriverIO, two commits were pushed as the project's bot account, which was allowed to bypass branch protection; StepSecurity says no WebdriverIO package release was affected. GitHub has published no statement on the campaign that this page could find. What is on record from GitHub is a hold, introduced in July, on potentially malicious workflow runs in public repositories. GitGuardian found that it held every November workflow-form run it could still see, seven of seven, and that the npm-hook form, which changes no workflow file, was not held and ran (public job logs from 19 repositories). StepSecurity's surviving Nextcloud run shows that the shell-script form ran too.

4,837 accounts opened probe pull requests in 61,764 repositories (Aikido); SafeDep's own search found 4,833 accounts and 61,734 repositories
8,093 public default branches received a payload commit by 04:36 UTC on November 12 (SafeDep); Aikido has indications that the payload ran in "at least 1,806" repositories
Azure and AWS footholds built to outlive a secret rotation, attempted where permissions allow: wfx-ci- federated credentials in Azure, an AWS role opened to any AWS account, and access keys for up to two IAM users
No actor named; Aikido assesses wfx and GhostAction as "distinct campaigns likely carried out by different threat actors"

This page rests on security vendors' write-ups (Aikido, StepSecurity, SafeDep, Endor Labs, GitGuardian, Semgrep, OX Security and Corgea), the Cloud Security Alliance's research note, Fly.io's notice and one repository owner's comment. They agree on the mechanism and differ on the counts and on the order of clean-up. Every source is linked so you can read it directly.

🔑 Credential Exposure: Tokens From More Than One Place
01
The operator held working GitHub tokens for thousands of accounts; how it got them is unconfirmed for the campaign as a whole, but one subset leaked from .git/config files that some apps hosted on Fly.io served to the internet
T1552.001 - Unsecured Credentials: Credentials In Files

No source says how most of the tokens were obtained. Endor Labs: "How the credentials were stolen has not been confirmed for the campaign as a whole." The Cloud Security Alliance's research note calls it "unconfirmed for the campaign as a whole." Semgrep says the operator used "GitHub tokens stolen in earlier breaches", and that "how they first obtained them remains unknown." StepSecurity: "Most of the campaign's activity uses other credentials, such as personal access tokens." In two of the cases it examined, drunomics and WebdriverIO, "the token the attacker used belonged to a bot."

One subset has an explanation. StepSecurity found that 173 of the probe pull requests, opened from 19 accounts, were made through the Fly.io GitHub App. Fly.io's notice of November 12 says its deploy-from-GitHub process "left a GitHub access token in the .git/config file of the build directory." "Some apps include the whole build directory in their image and serve it over HTTP," and for those apps the file and the token in it "could be fetched from the app's public URL." Fly.io is explicit: "To be clear: Fly.io's systems were not breached." It counts "more than 250 in total" probe pull requests in affected customers' repositories, made with tokens "belonging to a small number of Fly.io accounts", and it started revoking all user tokens issued to its GitHub App, for every customer. In an addendum on November 13 it said that GitHub support "acknowledged the process had started and then stopped partway through."

Two more pieces come from a victim and a researcher. The owner of the repository StringKe/kxen wrote on the probe pull request there that it was created "with a leaked GitHub CLI OAuth token". GitGuardian found that "431 of the accounts used in the wfx campaign, about 20%, were already compromised in the GhostAction wave", an earlier credential-theft campaign it tracks, and the CSA note, citing Aikido, counts more than 100 repositories where the wfx payload was injected into GhostAction's leftover workflow files. Shared accounts do not show a shared operator: Aikido assesses "these are distinct campaigns likely carried out by different threat actors." No wfx source traces the tokens to infostealer logs, which is where Hudson Rock traced many of Megalodon's, though GitGuardian lists infostealer logs among the ways stolen GitHub credentials in general are traded and reused.

This page maps the Fly.io subset, a token in a file served to the internet, to Credentials In Files. The rest of the tokens have no known origin and no technique here. What they share is that each was long-lived, carried write access, and still worked when the operator used it.

Confirmed for the campaign as a whole: no ("has not been confirmed", Endor Labs; "unconfirmed", CSA)
Fly.io subset: 173 probe pull requests from 19 accounts through the Fly.io GitHub App (StepSecurity); "more than 250 in total" (Fly.io)
How those leaked: a GitHub token in the build directory's .git/config, served over HTTP by apps that shipped the directory
One owner's account: a leaked GitHub CLI OAuth token (StringKe/kxen)
Other credentials: mostly personal access tokens; bot tokens at drunomics and WebdriverIO (StepSecurity)
GhostAction overlap: 431 accounts, about 20% (GitGuardian); distinct campaigns, per Aikido
Why it worked: long-lived tokens with write access stayed valid after they leaked

⚡ Initial Access: A Pull Request That Tests the Token
02
With each token the operator opened a pull request titled "docs: dependency audit notes" from a branch named wfx-docs, adding a two-line Markdown file, to confirm it could write to the repository
T1078 - Valid Accounts

StepSecurity describes the probe: a pull request titled docs: dependency audit notes, with the body "Routine dependency audit notes.", from a branch named wfx-docs, adding a two-line file, docs/wfx-audit.md, that is byte-identical in every pull request StepSecurity checked. Endor Labs: "Its job is to confirm write access." Its attack chain adds a second purpose: "It tests write access and triggers PR workflows." The owner of StringKe/kxen reads it the same way, writing that "its purpose was to trigger pull_request workflows against the poisoned default branch."

Aikido counts 4,837 accounts and 61,764 repositories for probe pull requests opened between 12:45 UTC on November 10 and 15:00 UTC on November 11, and 10,431 of the pull requests went to repositories the account did not own, reached through collaborator or organization access. SafeDep: "A probe pull request on its own means the account is compromised, even if no payload commit followed." Most were left in place: Aikido found 92% still open, which it says suggests most owners have not noticed. Nothing was exploited here; the token was valid and carried write access. This page maps the probe to Valid Accounts. ATT&CK has no technique for testing what a token can do.

Title: docs: dependency audit notes
Body: "Routine dependency audit notes."
Branch: wfx-docs
File: docs/wfx-audit.md, two lines, byte-identical in every pull request StepSecurity checked
Purpose: confirm write access (Aikido, Endor Labs); trigger pull_request workflows (Endor Labs, StringKe/kxen's owner)
Scale: 4,837 accounts, 61,764 repositories, 10,431 pull requests in repositories the account did not own (Aikido)
Why it worked: a valid token with write access needs nothing more

🧪 Execution: Four Ways Into the Repository's CI
03
In a subset of the probed repositories the operator pushed the stealer, authored as a real user of the repository, in one of four forms; three went straight to the default branch, and two change no workflow file
T1677 - Poisoned Pipeline Execution

StepSecurity and GitGuardian describe four ways the same script, about 1,500 lines of shell, reached a repository's CI (Aikido, SafeDep and Endor Labs list three, leaving out the shell-script form). The first, a commit titled ci: refresh build cache, adds two steps to an existing workflow: one, "Pass runtime", uses actions/github-script@v7 to export the Actions runtime tokens, and the other runs the script with WF_SECRETS: ${{ toJSON(secrets) }} and WF_VARS: ${{ toJSON(vars) }}, handing it every secret and variable. The second appends the script to a shell script the repository already runs, as at Nextcloud, where it went into update.sh. The third, chore: add dependency audit workflow, adds a new workflow file, build-audit-<6 characters>.yml, that runs on every push, with permissions that include id-token: write (SafeDep). It went on a throwaway chore/<8 characters> branch (Aikido, StepSecurity, GitGuardian), except in empty repositories, where SafeDep found it pushed to the default branch after a chore: initial commit. The fourth, chore: add ci helper, adds a hidden .ci-<6 characters>.sh and a package.json script, usually postinstall, which SafeDep notes runs on each npm install, on developers' laptops as well as in CI. The first, second and fourth forms went straight to the default branch.

"The commits are authored as real users of the repository, with their noreply email and no signature," SafeDep says, a pattern it reads as pointing to stolen tokens. Endor Labs calls them sandwich commits: "The theft happens on the default branch, wrapped between two ordinary-looking commits." At WebdriverIO, StepSecurity says, the two chore: add ci helper commits were pushed as the project's bot account, wdio-bot, "which was allowed to bypass branch protection." StepSecurity, SafeDep and OX Security count 28 WebdriverIO repositories reached through that bot (Endor Labs says 20). No source cites a WebdriverIO run that completed; Endor Labs' case study says "The script sent secrets and cloud credentials to 194.150.166[.]244:8080/exfil" without citing a run, and StepSecurity says "no WebdriverIO package release was affected."

GitHub's newest control stopped some of this. Since July 28, 2026, GitHub Actions has held potentially malicious workflows for approval, a protection that "currently applies to public repositories on github.com only." GitGuardian found it held the workflow forms: "Every November payload run we could still observe was put in action_required and never started", seven of seven. The npm-hook form got past it. GitGuardian says the hook version "does not change any workflow file" and that "GitHub's hold never applies, which we validated by observing the public job logs": of 30 repositories that ran jobs on the hook commit, none was blocked, and it has job logs from 19 where the script executed. The shell-script form changes no workflow file either, and it ran at Nextcloud, where StepSecurity found the surviving run. Nor does the hold cover private repositories, and Aikido says the code's handling of private repositories "suggests that the payload may be being deployed in private repositories." A payload commit is therefore not proof that the payload ran (step 10).

The script can also forge required status checks. Aikido: "the payload posts forged success status checks against the commit SHA", which clear branch protection because it matches on the check's name rather than on the app that posted it. StepSecurity found the feature switched off: "None of the 101 copies we examined had this turned on." This page treats it as a capability, not something observed. It maps the payload commits to Poisoned Pipeline Execution: the operator changed what the repository's own CI runs.

Form 1: ci: refresh build cache, two steps added to an existing workflow on the default branch (7,309 repositories, SafeDep; may include form 2, which uses the same commit message, per Semgrep's note on counts by that message)
Form 2: ci: refresh build cache, the script appended to a shell script CI already runs (Nextcloud's update.sh)
Form 3: chore: add dependency audit workflow, a new build-audit-*.yml on a throwaway chore/* branch (Aikido, StepSecurity, GitGuardian); on the default branch in empty repositories (16, SafeDep)
Form 4: chore: add ci helper, a hidden .ci-*.sh plus an npm postinstall script (771 repositories, SafeDep)
Author: a real user of the repository, noreply email, unsigned (SafeDep)
GitHub's approval hold: held every visible November workflow-form run, seven of seven (GitGuardian); form 4 not held and ran (GitGuardian); form 2 ran at Nextcloud (StepSecurity)
Capability, not observed: forged required status checks, off in all 101 copies StepSecurity examined
Why it worked: a push to the default branch, or a new on-push workflow on any branch, changes what CI runs, with no review, and a bot token could bypass branch protection

🔑 Credential Access: Runner Memory, Files and AI Keys
04
The stealer read the memory of the runner process that holds decrypted secrets, took every secret and variable when it ran from a workflow file, and swept other processes' environments, credential files and AI tool keys
T1003.007 - OS Credential Dumping: Proc Filesystem T1552.001 - Unsecured Credentials: Credentials In Files

Aikido, StepSecurity and SafeDep describe the same collection. When the script runs from a workflow file, the workflow hands it every Actions secret and variable, the job's GITHUB_TOKEN and the Actions runtime tokens; GitGuardian limits that route to the existing-workflow and new-workflow forms. In every form, where python3 is available (GitGuardian), it reads the memory of the runner's Runner.Worker process (Aikido and GitGuardian add Runner.Listener). StepSecurity says that process holds decrypted secrets, including ones the workflow never asked for, which, the CSA note explains, is why the shell-script and npm-hook forms can take secrets without editing a workflow. GitGuardian adds a limit: the memory scan "matches eight token families only", among them JWTs, GitHub, AWS and some AI provider tokens, so a secret in another format is taken only if it also sits in a process environment or a file.

It also reads other processes' environments under /proc and sweeps credential files for AWS, Azure, Google Cloud, Docker, Kubernetes, npm, PyPI, Git, SSH, GPG, Vault and Terraform, along with .env files, private keys and keystores, kubeconfig, Terraform variable and state files, shell histories and, SafeDep adds, cryptocurrency wallets. It looks for AI tool credentials too, for OpenAI, Anthropic, Gemini, Hugging Face, Cursor, Copilot and more. GitGuardian counts about 90 AI provider prefixes matched in environment variables, more than 90 fixed credential file paths plus a search of the home directory, and 92 secret patterns used to pick which repository files go into the archive. On self-hosted runners it also takes instance metadata credentials, container state and the runner's own credentials and RSA key (Aikido, GitGuardian). Nextcloud's job ran on one: StepSecurity says it "ran on Nextcloud's own server rather than one hosted by GitHub", so the stealer collected extra data from the machine itself, and Semgrep agrees. For self-hosted runners StepSecurity and the CSA note add the host's own credentials to the rotation list. The script also takes a snapshot of the repository and its last 100 commits.

The site's Mini Shai-Hulud page describes another campaign that read secrets from runner memory. No source links the actors; Semgrep remarks only that WFX "did learn something from Shai-Hulud." This page maps the memory read to Proc Filesystem and the file sweep to Credentials In Files.

Secrets (workflow forms): ${{ toJSON(secrets) }}, ${{ toJSON(vars) }}, GITHUB_TOKEN, Actions runtime tokens
Memory (every form): Runner.Worker (and Runner.Listener, per Aikido and GitGuardian), which holds decrypted secrets; the scan matches eight token families (GitGuardian)
Environments: /proc/*/environ
Files: cloud, container, registry, Git, SSH, GPG, Vault and Terraform credentials; .env, .pem, .p12, .jks, .kdbx, kubeconfig, *.tfvars, *.tfstate; shell histories; wallets
AI keys: about 90 AI provider prefixes in environment variables (GitGuardian)
Self-hosted runners: instance metadata credentials, container state, the runner's own credentials (Aikido, GitGuardian); Nextcloud's job ran on one (StepSecurity, Semgrep)
Why it worked: code on the default branch runs with the job's secrets, and the runner process holds more than the job asked for
Detect: on runners, a process reading another process's memory or every /proc/*/environ (this page's suggestion); GitHub's audit log event workflows.prepared_workflow_job "Includes the list of secrets that were provided to the job" (GitHub Docs; organizations only, and only through the REST API, audit log streaming or exports), a starting list for rotation (this page's suggestion)

🔀 Lateral Movement: GitHub's OIDC Token Into Three Clouds
05
The stealer minted GitHub OIDC tokens and tried to exchange them for AWS, Google Cloud and Azure access; where AWS accepted one, it chained from the first role into a second
T1550.001 - Use Alternate Authentication Material: Application Access Token

GitHub Actions can issue a job a short-lived OIDC token, and a cloud that has been told to trust GitHub as an identity provider exchanges that token for cloud credentials with no stored secret involved (this page's explanation). The stealer uses that path. In AWS it calls AssumeRoleWithWebIdentity for a role it finds named in the secrets, variables or repository, then assumes a further role, which Aikido and GitGuardian call the chained role; SafeDep says the sessions "are named wfx-<pid>". In Google Cloud it signs tokens with service-account keys it found and calls generateAccessToken and signJwt to impersonate service accounts. In Azure it exchanges OIDC tokens or client secrets for Azure Resource Manager tokens, lists subscriptions and Key Vaults and, per Aikido, replays refresh tokens from cached Azure CLI sessions against Microsoft's own client IDs for Graph, Resource Manager and Key Vault. It replays the OIDC token against Vault and Kubernetes too.

An OIDC token is issued to whatever runs in the job, so a cloud trust that admits any workflow in the repository admits the stealer, which runs from the default branch or, in one form, from a throwaway branch (this page's reading). The CSA note: "Cloud OIDC trust should be scoped as tightly as GitHub's subject claims allow." This page maps the use of the exchanged tokens to Application Access Token.

AWS: AssumeRoleWithWebIdentity, then AssumeRole into the chained role; sessions named wfx-<pid> (SafeDep)
Google Cloud: found service-account keys used to sign tokens; generateAccessToken and signJwt
Azure: Resource Manager tokens from OIDC tokens or client secrets; cached Azure CLI refresh tokens replayed (Aikido)
Vault and Kubernetes: the OIDC token replayed
Why it worked: cloud trust for GitHub OIDC admitted a workflow on a branch the stolen token could push to
Detect: in CloudTrail, AssumeRoleWithWebIdentity or AssumeRole with session name wfx-* (SafeDep, CSA); in Google Cloud, GenerateAccessToken and SignJwt from the GitHub workload identity pool; JWT logins to Vault, and Kubernetes secret reads, by identities from token.actions.githubusercontent.com (StepSecurity, GitGuardian; Vault also SafeDep, CSA)

🪝 Persistence: A Federated Credential on Azure App Registrations
06
Where its Azure token can write app registrations, the stealer tries to add federated identity credentials named wfx-ci-<n> that let a workflow on one branch of the compromised repository, main in SafeDep's samples, sign in as the app
T1098.001 - Account Manipulation: Additional Cloud Credentials

Aikido: "it adds new federated identity credentials, named wfx-ci-…, to Azure AD applications", pointing back to the compromised repository. StepSecurity gives the name as wfx-ci-<n>. A federated identity credential tells Entra ID to accept a token from an outside issuer, here GitHub's OIDC issuer, for a named subject, in place of a client secret or certificate (this page's explanation). SafeDep spells out the effect: "Any workflow on the repository's main branch can then log in to Azure as that app, even after you rotate client secrets." Aikido says such a workflow "can then authenticate to Azure without a stored secret, even after every token has been rotated."

The sources word the trusted branch differently. SafeDep and the CSA note name the repository's main branch; Aikido writes "Any workflow in that repository", and StepSecurity "trusting workflows in the compromised repository." Corgea's excerpt of the code sets the credential's subject to ref:refs/heads/${WF_REF:-main}, so the branch is whichever one the payload copy is configured with, main unless set otherwise, and main in SafeDep's samples.

The step works only where the identity the stealer obtained may write to app registrations. No source says it grants the app new permissions, so a later sign-in gets whatever roles and Microsoft Graph permissions the app already held (this page's reading). No source reports a wfx-ci- credential found in a victim tenant.

This credential is tied to GitHub. Using it takes a workflow run on that branch of that repository, so revoking the hijacked account's write access also blunts it. The CSA note puts the risk that remains: it "grants renewed access to anyone who later regains write access to that repository, whether the original attacker or someone holding another compromised account." Delete it either way. This page maps it to Additional Cloud Credentials, which covers credentials added to applications and service principals; ATT&CK does not name federated credentials.

Name: wfx-ci-<n> (StepSecurity); wfx-ci-… (Aikido)
Added to: Azure app registrations the stolen token could write
Trusts: GitHub OIDC tokens for workflows on the branch the payload names in the compromised repository: main in SafeDep's samples (SafeDep, CSA); "Any workflow in that repository" (Aikido); subject ref:refs/heads/${WF_REF:-main} (Corgea)
Survives: rotation of client secrets (SafeDep); "even after every token has been rotated" (Aikido)
Depends on GitHub: yes; it needs a workflow run on that branch, and grants renewed access to anyone who regains write access (CSA)
Found in a victim tenant: no source reports one
Why it worked: an identity with write access to app registrations was reachable from CI
Detect: Entra ID audit events that add a federated identity credential; az ad app federated-credential list --id <app-id> on every app registration (this page's suggestion), deleting any wfx-ci-* you did not create (StepSecurity, SafeDep, CSA, Endor Labs)

🪝 Persistence: An AWS Role Opened to Any Account, and New Keys
07
In AWS the stealer tries to set the chained role's trust policy to admit any AWS account and to create access keys for up to two IAM users; where it succeeds, the changes do not depend on GitHub
T1098 - Account Manipulation T1098.001 - Account Manipulation: Additional Cloud Credentials

Aikido: "It sets the chained role's trust policy to "Principal": {"AWS": "*"}, which opens the role to any AWS account." StepSecurity: "It rewrites an assumed role's trust policy to "Principal": {"AWS": "*"}". GitGuardian is more cautious: the code "tries to rewrite the chained role's trust policy." The role changed is the second one in the chain, not the role that GitHub's OIDC trust admitted, and the sources describe the policy being set to that principal, not a condition on the OIDC trust being loosened. The CSA note qualifies the result: such a role "can be assumed from any AWS account in the world (absent restrictive trust-policy conditions)". The change succeeds only if the session is allowed to update that role's trust policy (this page's explanation).

Separately, GitGuardian says the code "lists IAM users and calls iam:CreateAccessKey for up to two of them", and Aikido that it calls iam:CreateAccessKey "to create long-lived credentials for IAM users." An IAM user's access key works until someone deletes it.

Neither change involves GitHub. The CSA note calls the open role "immediate access that is independent of GitHub", and the access keys are standalone credentials (this page's reading), so revoking the hijacked GitHub account and rotating GitHub secrets leave both in place; they have to be found and removed in AWS. As with Azure, no source reports a rewritten role or a created key found in a victim's account. ATT&CK has no technique for replacing a role's trust policy, so this page maps it to the parent Account Manipulation; Trust Modification (T1484.002) concerns domain and tenant federation trusts and fits less well. The access keys map to Additional Cloud Credentials, whose page names CreateAccessKey.

📦 Exfiltration: A Bare IP on Port 8080, Then Telegram
08
The stealer packed what it found into one gzipped archive and posted it to a bare IP address on port 8080; from November 12 new copies also sent it to a Telegram bot, and later only there
T1041 - Exfiltration Over C2 Channel T1567 - Exfiltration Over Web Service

StepSecurity describes the deployed configuration: one gzipped tarball, sent by HTTP POST to 194.150.166[.]244:8080/exfil or 18.143.168[.]96:8080/exfil with a callback token, and later to 153.75.82[.]159:8080 alongside Telegram. "Telegram first appears in our samples at 01:10 UTC on November 12", and in StepSecurity's samples, "From about 05:30 UTC, new copies send stolen data only to a Telegram chat and carry no collection IP at all." Other vendors saw it earlier: GitGuardian dates its first Telegram-only copy to 01:48 UTC, and Endor Labs a Telegram-first test build to 01:52. The owner of StringKe/kxen wrote, in a notice on the probe pull request, that the attacker's workflow change read all Actions secrets and sent them to 18.143.168.96; the notice names no run in kxen. Nextcloud's surviving run log shows an 8,971-byte archive (archive_bytes 8971) and no retry message, from which StepSecurity concludes that the first upload, to 194.150.166[.]244, succeeded; Semgrep agrees. The code also carries channels inside GitHub, among them the Actions cache, the job's step summary and an artifact named wfx-loot-<run id>; Aikido and SafeDep say those were switched off in the copies they examined.

A runner allowed to reach only the hosts its builds need would have refused both (this page's reading). 🧹 Stealth: Revert, Then Delete the Run
09
Usually within a minute the operator pushed a revert titled "ci: restore" and deleted the workflow run with its logs, leaving a gap in the run numbers as the main trace
T1070 - Indicator Removal

Aikido: "the threat actor reverts within at most one minute and deletes the workflow run, along with its logs." StepSecurity's summary says "usually within a minute", and its examples vary: at zerosoul/rc-bullets "The revert landed two minutes later." The revert commit is titled ci: restore, sometimes ci: cleanup. Aikido and GitGuardian attribute the deletion to the actor, and it did not always happen: GitGuardian says "The actor deletes most payload runs." At Nextcloud, Semgrep writes, "The attacker's plan to clean up their mess failed, so the run log survived", and a Nextcloud developer reverted the commit 27 minutes later. At drunomics the revert came 12 seconds after the payload commit, and the Actions history "goes from run #1963 straight to run #1965. Run #1964, the run for the injected commit, is gone" (StepSecurity); Semgrep calls #1964 "the one that executed the stealer".

Endor Labs: "Because the payload sits on the default branch for only seconds, a scan of the current code finds nothing." What remains is history. StepSecurity: "The gap is the most reliable sign that the stealer ran." GitGuardian sets a limit on that: "A gap in run numbers proves a run was created. It does not prove the run executed." Of 65 November injection commits it examined, 37 have a gap in the workflow's run numbers at the payload commit. In an organization, GitHub's audit log records a deletion as workflows.delete_workflow_run, "A workflow run was deleted." The probe pull requests and wfx-docs branches were mostly left in place. This page maps the run and log deletion to Indicator Removal, under Stealth in ATT&CK v19.

📊 Scale: Three Stages, Counted Different Ways
10
The published counts disagree because they count different stages: repositories probed, repositories that received a payload commit, and repositories where there are signs the payload ran

Read the counts as three stages, each smaller than the last (this page's framing): an account probed a repository with a pull request; in some of those the operator pushed a payload commit; in some of those the payload ran. Each source counts a different stage, by its own method and at its own time, and the campaign was still running when they searched. Each count below keeps its source's wording of what it measures.

Probed, Aikido: "4,837 compromised accounts opened probe pull requests in 61,764 repositories", from 12:45 UTC on November 10 to 15:00 UTC on November 11
Probed, SafeDep: "61,879 of these pull requests in 61,734 repositories, opened from 4,833 accounts"
Probe pull requests, StepSecurity: "more than 63,000", a count of pull requests, not repositories
Received a payload commit, SafeDep: "8,093 repositories received malicious commits" between 12:46 UTC on November 10 and 04:36 UTC on November 12, counting public default branches only; by form 7,309 existing workflow, 771 npm hook and 16 new workflow in empty repositories, which sums to 8,096; the 7,309 may also take in the shell-script form, which shares the ci: refresh build cache message (see Semgrep's note below)
Payload patches, GitGuardian: "28,500 payload patches from 2,367 accounts across 17,715 repositories" in its own dataset; window not stated
Payload commits, StepSecurity: "more than 21,000 commits" titled ci: refresh build cache, a count of commits, not repositories, and one that, Semgrep notes, "also includes the next variant", the shell-script append
Pushed, StepSecurity: the stealer goes "only where the token's permissions and the repository's setup let it run, which is thousands of repositories"; no exact count (its 63,000 counts probe pull requests)
Ran, Aikido: "indications that the payload ran in at least 1,806 repositories, but this number may understate impact"; the same article also says "At least 1,835 repositories ran the payload and have had credentials exfiltrated", and explains neither method

Three cautions apply. SafeDep's 8,093 is a floor for its own stage: "Private repositories and other branches are missing, so the true total is higher." Receiving a payload is not running it. SecurityWeek notes of that count that it "does not necessarily indicate successful execution", and GitGuardian found that GitHub's approval hold stopped every visible November workflow-form run, seven of seven, while the npm-hook form was not held and ran; StepSecurity's surviving Nextcloud run shows the shell-script form ran too. And the counts of runs are floors because the operator deleted most runs and their logs (step 09). At the other end, SafeDep treats the probe alone as enough to act on: "A probe pull request on its own means the account is compromised, even if no payload commit followed." GitGuardian also traces an earlier wave, from October 24 to 29: "80 payload patches, 7 accounts, 12 repositories, all four delivery forms."

📦 Supply Chain: A Release From a Hijacked Publisher
11
Some hijacked accounts publish packages, and at least one release, Packagist's digitalelvis/neuronai-studio 3.14.3, shipped the stealer, though only an npm install inside the installed package runs it
T1195.002 - Compromise Software Supply Chain

Aikido: "At least 50 compromised users appear to publish packages for ecosystems including npm, Go, Packagist, PyPI or crates." It lists Packagist digitalelvis/neuronai-studio version 3.14.3 as malicious. SafeDep shows the sequence in that repository on November 11: the payload and a postinstall hook committed, the tag v3.14.3 pushed, and a revert eight seconds later. SafeDep says its data "does not show who ran" the release, the owner or the attacker. The release ships the hidden script and its postinstall hook, which run only when someone runs npm install or npm ci inside the vendored package; composer install does not run them (StepSecurity, SafeDep, CSA). Aikido and Endor Labs still advise treating machines that installed the compromised Packagist version as compromised. Go module versions from hijacked accounts also carry the payload, but only in a workflow file, which a Go build does not run, and SafeDep's scan of "218 npm, Go and Packagist packages whose source repositories received malicious commits" found no further malicious versions, without checking PyPI. This page maps the release to Compromise Software Supply Chain.

🚨 Detection: Vendors, a Hosting Provider and One Owner
12
Security vendors searching GitHub put the campaign on record on November 12, Fly.io started revoking its app's tokens the same day, and GitHub has said nothing public about it that this page could find

SafeDep says Aikido first reported the campaign. Aikido, StepSecurity, SafeDep, Endor Labs, Semgrep, OX Security and Corgea published on November 12, as did the CSA note, and GitGuardian followed on November 13. Their counts come from searching GitHub for the probe pull requests and the payload commits, which stayed in public history after the reverts. The owner of StringKe/kxen had already posted a notice on November 11 saying that the attacker's workflow change read all Actions secrets and sent them to 18.143.168.96, with the advice: "If you maintain this repository, treat every Actions secret it had on 2026-11-10 as compromised and rotate it."

Fly.io says it learned on November 12 that tokens issued to its GitHub App had been used by an unauthorized party. It notified the affected customers, started revoking all user tokens issued to the app, and changed its deploy process so that .git is no longer included in images built from GitHub. On November 13 it reported that GitHub's bulk revocation had "started and then stopped partway through."

GitHub has published no statement on the campaign that this page could find, and no source reports GitHub suspending the compromised accounts or revoking their tokens in bulk. Its July hold on potentially malicious workflows held the workflow-form runs GitGuardian could see; CSO Online says it "worked as designed for the payloads it could see." StepSecurity's summary of the root cause: "The attacker does not exploit a bug in GitHub Actions."

🛡 How to Defend Against This Chain

Revoke the hijacked account's access, and choose the order on purpose. The sources disagree on order. SafeDep puts the account first: "Revoke the commit author's tokens, OAuth app grants, SSH keys and sessions, and turn on 2FA. That account is the likely entry point." Endor Labs also locks the accounts before rotating, and the CSA note lists the account ahead of rotation. StepSecurity and GitGuardian list rotation first and the account later, and GitGuardian adds that "Rotating the secrets the payload stole is not enough." The order matters because while the account can still push to the repository, the operator can push the stealer again and capture the secrets you have just rotated. This page suggests revoking the account's tokens, OAuth grants, SSH keys and sessions first, or in the same hour as rotation, and removing any bot's branch-protection bypass at the same time (this page's reasoning). If you deploy to Fly.io from GitHub, check that https://<your-app>.fly.dev/.git/config returns nothing, as Fly.io advises.
Rotate everything the job could reach, not only what it used. "Where the payload ran, responders should rotate every secret the job could reach, not just those it referenced," says the CSA note, because the stealer read the runner's memory as well as the job's own secrets. That covers repository, environment and organization secrets, registry tokens, cloud keys and AI service keys, and on a self-hosted runner the host's own credentials (StepSecurity, CSA). In an organization, GitHub's audit log event workflows.prepared_workflow_job lists the secrets that were provided to each job, available only through the REST API, audit log streaming or exports (GitHub Docs), which gives you a starting list. Treat developer machines that ran npm install on an affected commit as compromised (StepSecurity, SafeDep, GitGuardian, CSA).
Remove the cloud persistence yourself, because rotation leaves it in place. StepSecurity's heading says it: "Remove the persistence, because rotation alone does not." In Entra ID, list the federated identity credentials on every app registration (az ad app federated-credential list --id <app-id>) and delete any wfx-ci-* you did not create. In AWS, find roles whose trust policy names "AWS": "*" and restore the intended policy, delete IAM access keys created since November 10 that you cannot account for, and search CloudTrail for AssumeRoleWithWebIdentity or AssumeRole sessions named wfx-* followed by CreateAccessKey or UpdateAssumeRolePolicy (SafeDep, CSA). In Google Cloud, look for GenerateAccessToken and SignJwt from the GitHub workload identity pool, and in Vault and Kubernetes for JWT logins from token.actions.githubusercontent.com. Do the AWS part before or together with rotation (this page's suggestion): the CSA note calls the open role's access "independent of GitHub", and new access keys stand alone too, so nothing on the GitHub side touches either.
Find what was pushed and what it left behind. Search every repository your developers can write to (Endor Labs) for the probe pull request (docs: dependency audit notes from wfx-docs), the commit titles ci: refresh build cache, chore: add ci helper, chore: add dependency audit workflow and ci: restore, and gaps in workflow run numbers. Because the code can forge required checks, look for commit statuses with the description wfx (GitGuardian), review the status checks posted on the attacker's commits (Endor Labs), and check that no commit was merged on the strength of a check the attacker marked as passed (StepSecurity). Endor Labs also suggests rulesets that expect each required check from a specific GitHub App. Close the probe pull requests and delete the wfx-docs and chore/* branches (StepSecurity, Endor Labs).
Make the default branch refuse a lone token. Three of the four forms arrived as a direct push to the default branch. The CSA note's hardening list: require review for pushes to default and release branches, extend CODEOWNERS to the scripts and manifests CI runs, include admins in branch protection and audit the bypass lists, make GITHUB_TOKEN read-only by default, and keep deployment secrets in environments that need approval. Default-branch protection does not stop the new-workflow form, which went on a throwaway chore/<8 characters> branch (Aikido, StepSecurity, GitGuardian) and runs on any push; in public repositories GitHub's approval hold caught the workflow forms (GitGuardian), and secrets kept in environments that need approval are not handed to a workflow on an arbitrary branch (this page's reading). A bot allowed to bypass branch protection, as at WebdriverIO, skips all of it.
Scope the cloud's trust in GitHub, and alert on anything that changes it. "Cloud OIDC trust should be scoped as tightly as GitHub's subject claims allow" (CSA). Trusting a subject that names a protected deployment environment, rather than any ref in the repository, means a push to the default branch alone does not get the role (this page's suggestion). Do not let a role CI can reach rewrite trust policies or create IAM user keys; an organization policy that denies iam:UpdateAssumeRolePolicy and iam:CreateAccessKey outside an administration path does that (this page's suggestion). And, in the CSA note's words: "Alerting on any creation or modification of federated identity credentials and IAM trust policies".
Do not run lifecycle scripts in CI, and limit where runners can send data. The CSA note: "Teams should also use npm ci --ignore-scripts where feasible, alert on newly introduced lifecycle hooks". The npm-hook form runs on developers' laptops as well as in CI, and it got past GitHub's workflow hold because it changed no workflow file (GitGuardian). On runners, allow outbound traffic only to the hosts your builds need; the CSA note: "Runner egress to the three collection IPs and to api.telegram.org should be blocked unless business-justified."
Keep the audit trail where the token cannot reach it. The operator deleted most runs and their logs with the same token that pushed the code. Stream the organization audit log off GitHub (CSA), alert on workflows.delete_workflow_run, and keep the run logs you would need for an investigation outside GitHub (this page's suggestion). Personal repositories have no organization audit log. For them, Fly.io advises looking for workflow runs you did not start, "including deleted runs in your GitHub security log", alongside the gap in the run numbers.
