Storm-0501 Cloud Ransomware 2025

Step-by-step kill chain mapped to MITRE ATT&CK Cloud, sourced from official post-mortems and primary technical analyses.

August 2025 Critical Azure

Storm-0501 - Domain Admin On Premises → Entra Connect Sync Pivot → Synced Global Admin With No MFA → Owner of Every Subscription → Exfiltrate, Delete Backups, Encrypt → Ransom Over Teams

On August 27, 2025 Microsoft Threat Intelligence described a recent intrusion by Storm-0501, which it calls a financially motivated threat actor, against an organization it does not name: "a large enterprise composed of multiple subsidiaries, each operating its own Active Directory domain." The subsidiaries kept separate Azure tenants with varying Microsoft Defender coverage. Microsoft's account starts after the actor already held domain administrator rights on premises, so how it got in is not disclosed, and Microsoft gives no date for the intrusion beyond calling it recent. From there the actor moved through Entra Connect Sync servers into a second tenant, where a synced, non-human account held Global Administrator and had no MFA method registered. It reset that account's password on premises, let Password Hash Synchronization carry it to the cloud, registered its own MFA method, and signed in from a hybrid-joined server to satisfy Conditional Access. As Global Administrator it added a federated-domain backdoor, made itself Owner of every subscription, copied storage data out with AzCopy, deleted backups and storage accounts, removed resource locks and immutability policies in its way, encrypted what immutability still protected with a key from a new Key Vault, deleted the key, and demanded ransom over Microsoft Teams.

Microsoft's title calls this cloud-based ransomware, and its introduction says Storm-0501 runs such attacks "without relying on traditional malware deployment." Here the encryption was an Azure feature run at the actor's request, with no ransomware binary involved, though the actor still used tools: Evil-WinRM and AzureHound on the way in, and AADInternals once it held Global Administrator. One control held. In the first tenant, the actor's sign-ins as privileged users were blocked by Conditional Access and MFA, which Microsoft says suggests the actor held valid credentials but lacked a second factor or could not satisfy the policy conditions. Microsoft gives no data volume, ransom amount or dwell time, and does not say whether the encryption key was purged, whether the data was recovered, or whether the victim paid. Dark Reading made the last point explicit: "Microsoft did not say whether the victim paid."

Undated intrusion; Microsoft reported it on August 27, 2025 as "a recent campaign"
2 Entra Connect servers compromised, the second tied to a different tenant and AD domain
1 tenant with Defender for Endpoint deployed and one domain with significant coverage, "leaving portions of the network unmonitored," per Microsoft
Storm-0501, a financially motivated actor active since at least 2021, per Microsoft; MITRE ATT&CK group G1053

⚡ Initial Access: Domain Admin, by a Route Microsoft Does Not Describe
01
When Microsoft's account begins, Storm-0501 already holds domain administrator rights in one of the victim's Active Directory domains, and how it got them is not disclosed
T1078.002 - Valid Accounts: Domain Accounts

Microsoft says it focused its analysis "on the post-compromise phase," and that at that point the actor "had already achieved domain administrator privileges in the targeted domain." Its overview diagram compresses everything before that into one box, "Achieved initial access and escalated privileges to domain admin privileges," with no method attached. The intrusion carries no date either: Microsoft calls it "a recent campaign" in a post published August 27, 2025. Microsoft's earlier reporting on Storm-0501 covers other victims, and the 2025 post does not tie any of those entry routes to this one, so this page maps only the position Microsoft describes, a valid domain administrator account.

The victim's monitoring was uneven from the start. The subsidiaries kept separate Azure tenants "with varying Microsoft Defender product coverage." Only one tenant had Defender for Endpoint deployed, with devices from several AD domains onboarded under that tenant's license, and only one of the compromised domains had significant Defender for Endpoint deployment, "leaving portions of the network unmonitored." Microsoft says this fragmented deployment "created visibility gaps across the environment," and the next step shows the actor checking for them.

Date of intrusion: not given; "a recent campaign"
Defender for Endpoint: deployed in one tenant; significant deployment in one compromised domain
Detect: nothing Microsoft describes; its account starts after this point

🔀 Lateral Movement: Hosts Defender Could Not See
02
On premises the actor checked hosts for Defender, moved with Evil-WinRM, likely pivoted through an Entra Connect Sync server Defender did not cover, and ran DCSync
T1518.001 - Software Discovery: Security Software Discovery T1021.006 - Remote Services: Windows Remote Management T1003.006 - OS Credential Dumping: DCSync

On the few onboarded devices where Microsoft saw Storm-0501 activity, the actor ran reconnaissance before acting: sc query sense and sc query windefend, which ask for the Defender for Endpoint (Sense) and Microsoft Defender Antivirus (WinDefend) services. Microsoft reads this as "suggesting a deliberate effort to avoid detection by targeting non-onboarded systems." It also ran discovery with native Windows tools such as quser.exe and net.exe.

It moved laterally with Evil-WinRM, "a post-exploitation tool that utilizes PowerShell over Windows Remote Management (WinRM)." Earlier in the attack it had compromised an Entra Connect Sync server that was not onboarded to Defender for Endpoint. "We assess that this server served as a pivot point," Microsoft writes, with the actor establishing a tunnel through it. Entra Connect Sync is the server that synchronizes on-premises Active Directory with Entra ID, so the actor now sat on a machine that links the two directories.

The actor also ran DCSync, which uses directory replication to ask a domain controller for credential data. By impersonating a domain controller, Microsoft says, it "could request password hashes for any user in the domain, including privileged accounts." Microsoft does not say which hashes were taken or whether any were used later.

Discovery: quser.exe, net.exe
Movement: Evil-WinRM, PowerShell over WinRM
Pivot: an Entra Connect Sync server not onboarded to Defender for Endpoint, used to tunnel (T1572); Microsoft's assessment
Credentials: DCSync; which hashes were taken is not stated
Detect: Defender for Endpoint "Suspicious remote PowerShell execution", "Possibly malicious use of proxy or tunneling tool" and "Possible source of DCSync attack"; Defender for Identity "Suspected DCSync attack (replication of directory services)"

🔍 Discovery: Tenant 1 Mapped, and Conditional Access Holds
03
With the Entra Connect Directory Synchronization Account and AzureHound the actor mapped the first tenant, then tried to sign in as privileged users and was blocked
T1087.004 - Account Discovery: Cloud Account T1580 - Cloud Infrastructure Discovery

Entra Connect Sync works in Entra ID through its Directory Synchronization Account (DSA). The actor used that account, with AzureHound, "to enumerate users, roles, and Azure resources within the tenant." Microsoft does not say how the actor obtained the account's credential in this tenant.

The actor then "attempted to sign in as several privileged users." In Microsoft's words, "These attempts were unsuccessful, blocked by Conditional Access policies and multifactor authentication (MFA) requirements." Its reading is hedged: "This suggests that while Storm-0501 had valid credentials, they lacked the necessary second factor or were unable to satisfy policy conditions." Microsoft does not say where those credentials came from. This is the control in the chain that worked, and Microsoft's diagram marks it: "Initial attempts to compromise cloud environment blocked by conditional access and MFA." The actor's next moves were in a different domain and a different tenant.

🔑 Credential Access: A Second Entra Connect Server
04
The actor crossed into another AD domain, compromised a second Entra Connect server tied to a second tenant, extracted its sync account, and found a synced Global Administrator with no MFA method
T1552.001 - Unsecured Credentials: Credentials In Files T1087.004 - Account Discovery: Cloud Account

Microsoft says the actor "traversed between Active Directory domains" and moved laterally to compromise a second Entra Connect server, associated with a different Entra ID tenant and AD domain. It does not say how. The actor then "extracted the Directory Synchronization Account to repeat the reconnaissance process" in the second tenant. Microsoft names no tool or method for the extraction. ATT&CK's entry for AADInternals files theft of Entra Connect credentials under Credentials In Files, and Microsoft's detection list includes Defender for Endpoint's "Entra Connect Sync credentials extraction attempt" and Defender Antivirus signatures such as Behavior:Win32/DumpADConnectCreds.A!EntraConnect.

The reconnaissance in the second tenant found "a non-human synced identity" holding the Global Administrator role in Entra ID, and "this account lacked any registered MFA method." Microsoft does not say what the account was for. A synced account is managed from on-premises AD, and the guide from ASD's ACSC, CISA, NSA and partners spells out the consequence: an attacker who compromises AD DS and reaches a privileged user object that synchronizes to Entra ID gains access to Entra ID. Its rule is "Do not synchronise privileged user objects from AD DS to Microsoft Entra ID."

Why it worked: a cloud admin role on an account managed from on-premises AD

⬆️ Privilege Escalation: An On-Premises Reset Becomes a Cloud Sign-In
05
The actor reset the account's on-premises password, Password Hash Synchronization carried it to Entra ID, and the actor registered its own MFA method and signed in from a hybrid-joined server
T1098 - Account Manipulation T1098.005 - Account Manipulation: Device Registration T1078.004 - Valid Accounts: Cloud Accounts

The actor "reset the user's on-premises password," which Entra Connect Sync then "legitimately synced" to the account's cloud identity shortly afterwards. The service ran Password Hash Synchronization, which Microsoft calls "the most common mode," and in Entra ID the password change appears as made by the Directory Synchronization Account. Microsoft's 2024 post lists two routes for a synced account: reset its on-premises password and let sync carry it to the cloud, or use a stolen sync account to set the cloud password with AADInternals. The 2025 post describes the first. The guide from ASD's ACSC, CISA, NSA and partners warns that the sync account "could also be used to set the password for a user object with the Global Administrator role."

The password was not enough on its own. With no MFA method registered, the actor "was redirected to simply register a new MFA method under their control." Microsoft does not say which method type. A Conditional Access policy also required a hybrid-joined device, so the actor "had to move laterally between different devices in the network" until Microsoft saw a successful Azure portal sign-in as Global Administrator "coming from a server that was hybrid joined." Microsoft describes the actor meeting the policies, not changing them. MITRE's group page maps this to Modify Authentication Process: Conditional Access Policies, which covers changing policies, so this page maps it to Valid Accounts: Cloud Accounts instead.

Reset: the synced Global Administrator's on-premises password
Delivered by: Password Hash Synchronization; Entra ID shows the sync account making the change
MFA: none registered, so the actor registered its own; method type not stated
Device condition: hybrid joined, met from a compromised hybrid-joined server
Why it worked: a privileged account with no registered factor, and a device condition a compromised hybrid-joined machine meets

🔐 Persistence: A Federated Domain the Attacker Owns
06
As Global Administrator the actor used AADInternals to register a tenant it owned as a trusted federated domain, a backdoor for signing in as almost any user
T1484.002 - Domain or Tenant Policy Modification: Trust Modification T1606.002 - Forge Web Credentials: SAML Tokens

The actor used its Global Administrator rights and the AADInternals tool "to register a threat actor-owned Entra ID tenant as a trusted federated domain." Microsoft says the backdoor let it "craft security assertion markup language (SAML) tokens" and sign in "as almost any user, according to the ImmutableId user property." Microsoft's table of observed activity lists crafting access tokens and acting against the cloud with them, but its narrative does not tie a forged token to a particular later step.

A federation trust does not depend on the account that created it, so resetting that Global Administrator's password would leave the backdoor in place. Microsoft Incident Response's recovery playbook for Octo Tempest, a different actor that also plants federation backdoors, tells responders to "Change federation authentication from Federated to Managed" during eviction. The SolarWinds intruders also added trusted federated identity providers in Azure AD.

Tool: AADInternals
Change: an attacker-owned Entra ID tenant registered as a trusted federated domain
Capability: SAML tokens for "almost any user", matched on ImmutableId
Forged tokens used for: not tied to a later step by Microsoft
Harden: set validatingDomains in federatedTokenValidationPolicy to 'all' (Microsoft)
Detect: Defender for Cloud Apps "Backdoor creation using AADInternals tool"; Defender for Endpoint "Suspicious cmdlets launch using AADInternals"

⬆️ Privilege Escalation: Global Admin to Owner of Every Subscription
07
The actor called elevateAccess to become User Access Administrator over all the organization's subscriptions, made itself Owner of each, and mapped the protections it would meet
T1098.003 - Account Manipulation: Additional Cloud Roles T1580 - Cloud Infrastructure Discovery

Entra ID roles do not grant access to Azure resources, Microsoft Learn explains, but a Global Administrator can elevate across that boundary. The actor invoked Microsoft.Authorization/elevateAccess/action and gained the User Access Administrator role "over all the organization's Azure subscriptions"; Microsoft Learn says elevation assigns that role "at root scope (/)". It then "assigned themselves the Owner Azure role over all the Azure subscriptions available" with Microsoft.Authorization/roleAssignments/write.

Microsoft assesses that the actor then used AzureHound to locate the organization's critical assets. It "managed to map out the Azure environment," including Azure policies, resource locks and Azure Storage immutability policies, the protections the next steps ran into. Compare Storm-2949, where the compromised identities already held privileged Azure RBAC; here an Entra role became Azure Owner through two operations.

Elevate: Microsoft.Authorization/elevateAccess/action; User Access Administrator at root scope "/" (Microsoft Learn)
Assign: Microsoft.Authorization/roleAssignments/write; Owner on all subscriptions
Mapped: Azure policies, resource locks, Azure Storage immutability policies (AzureHound, in Microsoft's assessment)
Logged in: the Entra directory audit logs (in preview) and the Directory Activity view of the Azure activity log (Microsoft Learn)
Detect: Defender for Resource Manager "Suspicious elevate access operation" and "Suspicious Azure role assignment detected (Preview)"; Defender XDR "Possibly compromised user elevated access to Azure resources"

📤 Exfiltration: Open the Accounts, Take the Keys, Copy the Data
08
The actor opened storage accounts to the internet and its own infrastructure, read their access keys, and copied the data out with AzCopy
T1686.001 - Disable or Modify System Firewall: Cloud Firewall T1552 - Unsecured Credentials T1530 - Data from Cloud Storage

Storm-0501 "exposed non-remotely accessible accounts to the internet and to their own infrastructure" with Microsoft.Storage/storageAccounts/write. Microsoft files this under defense evasion; in ATT&CK v19 a cloud firewall change sits under Defense Impairment. For storage accounts with key access enabled, the actor used its Owner role to read the access keys through Microsoft.Storage/storageAccounts/listkeys/action, and "exfiltrated the data in these accounts to their own infrastructure" with the AzCopy command-line tool.

Microsoft gives no data volume and does not say what kind of infrastructure received the data, so this page maps the collection from cloud storage and leaves the exfiltration technique open: Transfer Data to Cloud Account and Exfiltration to Cloud Storage would each fit one reading. Microsoft ties the AzCopy copy to the exposure step and does not say whether it used the stolen keys, but an account key works without any Entra ID sign-in, which is why listkeys matters. In Storm-3168, Microsoft noted that the same key collection could enable future data access.

💥 Impact: Backups, Storage, and the Locks in the Way
09
The actor deleted snapshots, restore points, storage accounts and Recovery Services protection containers, and removed locks and immutability policies that stood in the way
T1490 - Inhibit System Recovery T1485 - Data Destruction T1685 - Disable or Modify Tools

The deletions covered recovery and data alike: Microsoft.Compute/snapshots/delete, Microsoft.Compute/restorePointCollections/delete, Microsoft.Storage/storageAccounts/delete and Microsoft.RecoveryServices/Vaults/backupFabrics/protectionContainers/delete. Microsoft names Recovery Services protection containers, not whole vaults. Across the Storm-0501 Azure campaigns it investigated, Microsoft says, this is "where they mainly focused, deleting as many Azure Storage account resources as possible."

Some deletions failed "due to the existing protections": resource locks and Azure Storage immutability policies. The Owner role could remove them. The actor called Microsoft.Authorization/locks/delete and Microsoft.Storage/storageAccounts/blobServices/containers/immutabilityPolicies/delete, succeeded for "multiple" locks and policies, and went on "successfully erasing resources in various Azure subscriptions." Microsoft does not say whether any of the policies were locked. Microsoft Learn draws the line that matters: an unlocked time-based retention policy can be deleted, while "You can't delete a locked time-based retention policy." In Storm-3168, by contrast, attempts to remove recovery locks failed.

Deleted: snapshots, VM restore point collections, storage accounts, Recovery Services protection containers
Blocked at first by: resource locks; Azure Storage immutability policies
Then removed: Microsoft.Authorization/locks/delete; Microsoft.Storage/storageAccounts/blobServices/containers/immutabilityPolicies/delete
Why it worked: Owner can delete resource locks, and an unlocked immutability policy can be deleted (Microsoft Learn)

💥 Impact: Encryption Scopes, a Deleted Key and a Teams Message
10
For data that immutability still protected, the actor encrypted it with a key from a new Key Vault it created, deleted the key, and demanded ransom over Microsoft Teams
T1486 - Data Encrypted for Impact T1657 - Financial Theft

"For resources that remained protected by immutability policies, the actor resorted to cloud-based encryption." It "created a new Azure Key Vault and a new Customer-managed key" (Microsoft.KeyVault/vaults/write) and applied it through storage encryption scopes (Microsoft.Storage/storageAccounts/encryptionScopes/write). Encryption alone "wasn't sufficient, as the organization could still access the data," Microsoft notes, so the actor deleted the key used for the encryption. Microsoft adds, as a general point, that Key Vault keys used for encryption are protected by soft delete, "with a default period of 90 days," which allows a deleted key or vault to be retrieved. It does not say whether the key was purged or whether the data was recovered. Microsoft Learn adds two platform rules that bear on this vault: a key vault holding an encryption scope's customer-managed key "must have purge protection enabled," so the key could not be purged before its retention period ended, and that period is set when the vault is created, anywhere from 7 to 90 days. Here the actor created the vault, so the actor chose the recovery window.

The demand came last: the actor "contacted the victims using Microsoft Teams using one of the previously compromised users, demanding ransom." Microsoft gives no amount and does not say whether anyone paid. Codefinger used the same idea in S3, encrypting with keys AWS never stores. Here the key lived in Key Vault, where soft delete and the purge protection that encryption scopes require kept a deleted key recoverable until the retention period ran out.

Created: a new Azure Key Vault and customer-managed key (Microsoft.KeyVault/vaults/write)
Applied: Microsoft.Storage/storageAccounts/encryptionScopes/write
Then: the key deleted
Recoverable: the soft-deleted key, for the retention period the vault's creator set (7 to 90 days; 90 by default)
Not stated: whether the key was purged, whether data was recovered, whether the ransom was paid
Demand: Microsoft Teams, from a previously compromised user
Detect: Defender for Key Vault "Unusual operation pattern in a key vault"

🛡 How to Defend Against This Chain

Run Entra Connect servers as Tier 0, with EDR on them. The actor used both Entra Connect servers in this chain, and the first was not onboarded to Defender for Endpoint. The guide from ASD's ACSC, CISA, NSA and partners says these servers "need to be afforded the same security as Domain Controllers," notes that Microsoft classifies them as Tier 0 assets in its Enterprise Access Model, and adds single-purpose servers and administration only through jump servers and secure admin workstations. Microsoft recommends enabling TPM on the Entra Connect Sync server "to securely store sensitive credentials and cryptographic keys, mitigating Storm-0501's credential extraction techniques," along with tamper protection and EDR in block mode, and using Exposure Management to identify the Entra Connect server, users with DCSync permissions and Global Administrators as critical assets. Microsoft also says the limited Defender for Endpoint deployment "significantly hindered detection," and on the devices Microsoft could see, this actor checked for Defender before acting, so find the domains, tenants and servers with no EDR, starting with Tier 0.
Keep Global Administrators in the cloud only. Microsoft's guidance is that "Global Administrator (and other privileged groups) accounts should be cloud-native accounts with no ties to on-premises Active Directory." The ASD-led guide agrees: "Use separate privileged accounts for AD DS and Microsoft Entra ID." In this chain a password reset on premises became a Global Administrator credential in the cloud. A review of synced accounts that hold Entra admin roles, non-human ones included, finds accounts like this one before an attacker does.
Register phishing-resistant MFA on every privileged account before anyone else can. The Global Administrator had no method registered, so the first sign-in with its password could enroll one. Microsoft's advice is to "Ensure all existing privileged users have an already registered MFA method to protect against malicious MFA registrations," and to require phishing-resistant authentication strength for administrators. Microsoft also recommends Entra ID Protection with risk-based Conditional Access. The hybrid-joined device condition here was met from a compromised server, so for admin roles this page reads a device condition as a complement to phishing-resistant MFA rather than a substitute for it.
Put the sync account behind Conditional Access, and move Entra Connect to application-based authentication. Microsoft recommends Conditional Access to "limit the access of Microsoft Entra ID Directory Synchronization Accounts (DSA) from untrusted IP addresses to all cloud apps," and, once Entra Connect uses application-based authentication, Conditional Access for workload identities. Application-based authentication arrived as a public preview in Entra Connect 2.5.3.0 on May 27, 2025, and Microsoft's version history requires Entra Connect Sync 2.6.84.0 or later with application-based authentication by April 7, 2027. Microsoft has also restricted the permissions of the Directory Synchronization Accounts role; Tenable dates that change to August 2024, before this intrusion was reported, and notes that "the role is still privileged," able among other things to "reset their password." Turn on the Defender for Cloud Apps connectors so the sync-account alerts can fire, and hunt for sync-account activity that leaves its usual pattern.
Limit what a federated-domain backdoor can reach. Microsoft recommends setting the validatingDomains property of federatedTokenValidationPolicy to 'all', which blocks SAML sign-ins to non-federated domains such as .onmicrosoft.com; Microsoft Graph documents that Entra ID then rejects a federated token whose account's root domain does not match the mapped Entra ID account. Microsoft also recommends, where only Entra ID performs MFA for a federated domain, setting federatedIdpMfaBehavior to rejectMfaByFederatedIdp. A Global Administrator can add a domain or change these settings, and adding a federated domain is a rare administrative act, so this page suggests alerting on any new federated domain or change to a domain's federation settings, alongside Microsoft's "Backdoor creation using AADInternals tool" detection.
Alert on elevate access, and remove it after use. One call to Microsoft.Authorization/elevateAccess/action gave an Entra role control of Azure role assignments at root scope. Microsoft Learn says to remove elevated access "once you have made the changes you need to make at root scope," records each elevation in the Entra directory audit logs (in preview) and in the Directory Activity view of the Azure activity log, and points to a Microsoft Sentinel rule template, "Azure RBAC (Elevate Access)". Microsoft Learn lists the entry under Directory Activity rather than in a subscription's activity log, so this page reads it as easy to miss for a pipeline that collects only subscription activity logs. Pair it with Defender for Resource Manager's "Suspicious elevate access operation" and an alert on new Owner assignments at subscription scope.
Give backups a protection the subscription Owner cannot remove. Owner rights deleted resource locks and immutability policies here, so a lock or an unlocked policy guards against mistakes and gives way to an attacker holding Owner. Microsoft's post recommends immutable blob storage, Resource Manager locks, blob backup and Azure Backup for VMs, and does not discuss locked policies. Microsoft Learn does: "You can't delete a locked time-based retention policy," a container under a locked policy can be deleted only when it is empty, and Microsoft recommends the unlocked state only for short-term testing. For Azure Backup, an immutable vault set to "Enabled and locked" can't be disabled, covers Recovery Services and Backup vaults, and blocks stopping protection with deletion of data, though Microsoft Learn notes it "doesn't apply to operational backups for resources like blobs, files, and disks." Locking is irreversible in both cases, so test the retention settings first.
Watch for new Key Vaults and encryption scopes, and recover soft-deleted keys in time. The key in this chain sat in a vault the actor created, so the victim's own vault settings did not govern it. An encryption scope with a customer-managed key requires a vault with purge protection, which kept the deleted key from being purged early, but the vault's creator sets the retention period when creating it, anywhere from 7 to 90 days. A responder should find vaults created during the intrusion and recover their soft-deleted keys before that period ends. Defender for Key Vault's "Unusual operation pattern in a key vault" covers the vault activity; this page adds an alert on new vaults or storage encryption scopes created outside the deployment pipeline. For the vaults you own, Microsoft recommends purge protection "to prevent immediate, irreversible deletion of vaults and secrets," with the default 90-day retention.
If you are responding to a chain like this, start the eviction in the cloud. Microsoft did not publish this victim's recovery steps. Microsoft Incident Response's playbook for hybrid identity compromise, written for Octo Tempest, begins "with the cloud eviction process": change federated domains back to managed authentication, revoke permissions from the old admin accounts and create new ones, then on premises reset the KRBTGT and built-in Administrator passwords twice each, reset inter-domain trust and DSRM passwords, and finish with a mass password reset. That is general practice for hybrid compromise, not a record of what this victim did.
