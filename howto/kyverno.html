Kyverno policies, hands-on

Kyverno checks requests to create, change or delete things in a Kubernetes cluster against rules you write, such as "no container may run as root", and the rules themselves are stored in the cluster like any other Kubernetes object. Since version 1.19 deprecated the older format, the logic inside those policies is written in CEL (Common Expression Language). Learn the current policy types with the free kyverno command-line tool, with no cluster, then learn to read the older ClusterPolicy that existing clusters still run.

Jump to the walk-through All how-to guides

Last updated 2026-11-06 · By Shawn Nunley

Time: ~2 hours  ·  Difficulty: Intermediate  ·  You need: the kyverno command-line interface (CLI), from Homebrew or a release download, and a terminal. Network access for step 10 only. No cluster and no cloud account.

How this page was checked: every command, policy and test on this page, including the exercise answers, was run as printed with the Kyverno CLI 1.19.2 (the Homebrew build) on an Apple silicon Mac, in zsh, and the outputs shown are what it printed, less its terminal colors. No cluster was used, because Docker was not available when the page was written, so everything said about a running cluster (webhooks, failure policies, timeouts, background scans and the report objects) comes from Kyverno's 1.19 documentation, its Helm chart and its source code; none of it was observed. Step 10 fetched real signatures from registry.k8s.io and the public Sigstore services. The GitHub Actions workflow in step 11 was not run on GitHub; its commands were run locally. The page was also run with the Kyverno 1.20.0-rc.1 CLI, published on 2 November 2026: it gave the same verdicts for every current policy type, with small differences in how it prints messages and test tables, and refused the legacy ClusterPolicy in step 12 and exercise 3 with an error saying that 1.20 no longer runs or accepts them.

Policies that are Kubernetes resources

A team that runs a Kubernetes cluster usually wants some rules to hold for every workload in it: no container runs as root, every image comes from a registry the team trusts, every new namespace starts with incoming traffic blocked until someone allows it. Kyverno enforces rules like those. It is an open-source (Apache 2.0) policy engine for Kubernetes, and a graduated project of the Cloud Native Computing Foundation (CNCF) since March 2026.

It runs inside the cluster as a handful of controllers, programs that watch the cluster and act on what they find. The admission controller is a webhook: before the API server (the part of Kubernetes that receives every request and stores the cluster's objects) stores an object, it sends Kyverno the create, update or delete request, and Kyverno can reject it, change it, or let it through. Other controllers scan resources that already exist and write what they find into reports, create resources on a trigger, and delete resources on a schedule.

A Kyverno policy is itself a Kubernetes resource: YAML you kubectl apply, review in git, and protect with RBAC (role-based access control) like any other object. Gatekeeper, the admission controller built on the Open Policy Agent (OPA), keeps its policies as Kubernetes resources too, and traditionally writes its checks in Rego, a separate policy language. Kyverno's checks are CEL, the expression language Kubernetes itself uses for admission policies.

There are two generations of Kyverno policy, and the difference decides what you should write today. The legacy generation, in the kyverno.io/v1 API, is ClusterPolicy and its namespaced twin Policy. Each holds rules that match resources by kind, then check them with YAML patterns and JMESPath expressions. Kyverno 1.19 (August 2026) deprecated them. Its documentation says they are removed in 1.20, and the 1.20 release candidate keeps existing objects readable but no longer runs them or accepts new ones. 1.19 is the last release that runs them.

The current generation, in the policies.kyverno.io/v1 API, has one policy type for each job: ValidatingPolicy checks a request, MutatingPolicy changes it, GeneratingPolicy creates other resources, DeletingPolicy deletes resources on a schedule, and ImageValidatingPolicy checks the signatures on container images. Each has a Namespaced variant. The logic is CEL, and a ValidatingPolicy has the same shape as Kubernetes' own ValidatingAdmissionPolicy, with more around it. They arrived in 1.14 and 1.15 and reached their stable v1 API in 1.17.

So this page writes the current types, and step 12 teaches you to read the legacy ones, which you will meet in running clusters, in blog posts and in older copies of Kyverno's policy library, and will need to migrate. Everything runs in the kyverno CLI, which applies any policy type to YAML files on your laptop at no cost. The CEL itself is covered on the CEL guide; this page assumes no more of it than it explains.

How to use this guide

This guide is marked intermediate. It assumes you know Kubernetes basics: that a Pod is one or more containers run together, that a Deployment keeps a set of identical Pods running, that namespaces divide up a cluster, and that YAML manifests describe all of these. The site's Kubernetes security guide explains Pods and namespaces, and its section on admission control shows where Kyverno fits. You need no cluster, and no CEL beforehand: the page explains each piece of CEL it uses.

Read the two short sections after this one before the walk-through. Five quiet ways a Kyverno policy does nothing lists the failures the walk-through demonstrates, and the section after it explains the chain a request passes through before a policy sees it. The walk-through then builds a lab in ~/kyverno-lab: step 1 installs the CLI, and step 2 saves five sample Pods and a Deployment. Most steps after that follow one pattern. You save a policy, run kyverno apply to judge the lab's files against it, compare what it prints with the page, and read why it came out that way. To show a quiet failure, several steps then make a broken copy of a policy with a sed line, which writes a copy of a file with one piece of text replaced. Steps 7 to 9 also describe what a running cluster does, which the CLI cannot show you, step 11 turns the checks into tests, and step 12 reads an older style of policy. The exercises run in the same folder, with each answer hidden until you open Show the answer.

Each input block has a label at the top, and every block has a copy button. A block labelled YAML is a file to save, under the name the sentence before it gives, and its first line, a comment, repeats the name. Save it in ~/kyverno-lab, or in the subfolder its name includes, such as policies/, creating that folder first if it does not exist. A block labelled BASH holds commands to paste into your terminal from ~/kyverno-lab. An unlabelled block is output: what the command before it should print. Many commands are followed by echo $?, which prints the exit status of the command before it. 0 means success and any other number signals a problem, and that number is what an automated check in a pipeline looks at.

Your output should match the page line for line, apart from colors. Every command, policy and test here, the exercise answers included, was run as printed with Kyverno CLI 1.19.2 in zsh, and the outputs are what it printed; step 10 read real signatures over the network. What the page says about a running cluster was not observed, because no cluster was used: the webhooks, failure policies, timeouts, background scans and report objects described in the two sections before the walk-through and in steps 7 to 9 come from Kyverno's documentation, Helm chart and source code. The GitHub Actions workflow in step 11 was not run on GitHub, though its commands were run locally, and nothing in the lab needs it until you keep policies in a repository. The 1.20 release candidate gave the same verdicts for every current policy type, printed slightly differently, but refuses the legacy policies in step 12 and exercise 3, which need a 1.19 CLI.

If your output differs, check that you are in ~/kyverno-lab, that kyverno version reports 1.19.2, the version the page used, and that policies/run-as-non-root.yaml holds step 4's version: step 4 replaces step 3's first attempt, and the steps after it use the replacement.

Five quiet ways a Kyverno policy does nothing

Suppose you apply a policy that refuses containers running as root, and a week later find one running anyway, with no error anywhere. Each of the five failures below can leave you there. A Kyverno policy that never sees the request it was written for raises no error and blocks nothing. These five are what this page is built around, and each is shown running in the step named. The list uses terms that those steps explain, so on a first reading take it as a map of what to watch for, and come back to it after the walk-through.

  1. It reports when you meant it to block. A legacy ClusterPolicy with no failure action defaults to Audit: the violating resource is created and the violation goes into a report. A ValidatingPolicy with no validationActions defaults to Deny, so a migration can flip a policy's behavior without anyone deciding to. The CLI reports a failure either way. (Steps 7 and 12.)
  2. The webhook fails open. With failurePolicy: Ignore, a request goes through unchecked whenever Kyverno is down or slower than the webhook timeout, which is 10 seconds by default. A GeneratingPolicy always works that way, and a default install leaves admission requests in kube-system, kube-public, kube-node-lease and Kyverno's own namespace unchecked. (Step 7.)
  3. The match never matches. Write Pods, pod or Pod where Kubernetes says pods, or name the wrong API group, and the policy judges nothing: the CLI prints zeros and exits 0. Add one exclusion to a Pod policy and it quietly stops checking Deployments. (Steps 5 and 6.)
  4. A missing field passes. orValue(true) in CEL and the =() anchor in a legacy pattern both pass a container that never set the field. A check on containers alone misses init and ephemeral containers, and an image check passes every image outside its glob. (Steps 4, 10 and 12.)
  5. Existing resources stay as they are. Admission judges requests, so a new policy affects only what is created or changed after it. What was already running is judged by the background scan, hourly by default, which writes reports and blocks nothing, even when the policy is set to deny. (Step 8.)

A policy judges only the requests it is sent

Three of those five happen before your expression ever runs. The one idea that makes Kyverno click is that your expression is the last step of a chain, and most failures happen earlier in the chain. In a cluster, an object reaches your policy's check only when every one of these is true:

  • The API server sends the request, and Kyverno keeps it. Kyverno registers webhooks for the operations and resources its policies match, minus the namespaces its install excludes, then drops any request its resource filters name. Anything else never reaches a policy. (Step 7.)
  • Kyverno answers in time. If its pods are down, or a policy takes longer than the webhook timeout, the webhook's failure policy decides, and nothing of yours runs. (Step 7.)
  • There is a request at all. Admission sees creates, updates and deletes. A Pod that was running before the policy existed sends nothing until someone changes it. (Step 8.)
  • The policy selects it. The match, any match conditions, and any exception all have to let it through to the check. (Steps 5 and 6.)

The CLI skips the whole chain. kyverno apply hands every resource file straight to every policy, so a clean run proves your expression is right and says nothing about whether the policy will see anything. Keep those two questions apart, whether the check is right and whether anything reaches it, and the rest of this page follows.

Walk-through

1. Install the CLI and make a lab

On macOS or Linux with Homebrew:

brew install kyverno
kyverno version
mkdir -p ~/kyverno-lab/policies && cd ~/kyverno-lab

The first line of kyverno version should read Version: 1.19.2 or later in the 1.19 series. Without Homebrew, download kyverno-cli_v1.19.2_ followed by your platform from the 1.19.2 release page, unpack it, and put the kyverno binary on your PATH. The 1.20 release candidate gives the same results for steps 2 to 11, printed slightly differently, and refuses the legacy policies in step 12 and exercise 3, which need a 1.19 CLI.

2. The lab: five Pods and a Deployment

The lab is one rule, "no container may run as root", and six resources that get it right or wrong in different ways. Kubernetes enforces it when a container's securityContext.runAsNonRoot is true, and a container that does not set it inherits the Pod's spec.securityContext.runAsNonRoot. Save this as pods.yaml:

# pods.yaml: five Pods, each getting runAsNonRoot right or wrong its own way
apiVersion: v1
kind: Pod
metadata: {name: web, namespace: shop}
spec:
  containers:
    - name: app
      image: ghcr.io/acme/web:2.1.0
      securityContext: {runAsNonRoot: true}
---
apiVersion: v1
kind: Pod
metadata: {name: root, namespace: shop}
spec:
  containers:
    - name: app
      image: ghcr.io/acme/web:2.1.0
      securityContext: {runAsNonRoot: false}
---
apiVersion: v1
kind: Pod
metadata: {name: unset, namespace: shop}
spec:
  containers:
    - name: app
      image: ghcr.io/acme/web:2.1.0
---
apiVersion: v1
kind: Pod
metadata: {name: inherits, namespace: shop}
spec:
  securityContext: {runAsNonRoot: true}
  containers:
    - name: app
      image: ghcr.io/acme/web:2.1.0
---
apiVersion: v1
kind: Pod
metadata: {name: init, namespace: shop}
spec:
  initContainers:
    - name: setup
      image: ghcr.io/acme/setup:0.9
  containers:
    - name: app
      image: ghcr.io/acme/web:2.1.0
      securityContext: {runAsNonRoot: true}

The right answers: web and inherits are compliant. root asks for root, unset never says, and init has a compliant app container behind an init container (one that runs to completion before the app containers start), setup, that may run as root. Save this as deploy.yaml, a Deployment whose Pod template never says either:

# deploy.yaml: a Deployment whose Pod template does not set runAsNonRoot
apiVersion: apps/v1
kind: Deployment
metadata: {name: api, namespace: shop}
spec:
  replicas: 2
  selector:
    matchLabels: {app: api}
  template:
    metadata:
      labels: {app: api}
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:3.0.2

3. Your first ValidatingPolicy

Save this as policies/run-as-non-root.yaml. It is a reasonable first attempt, and steps 4 to 6 find what is wrong with it:

# policies/run-as-non-root.yaml: first attempt
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: run-as-non-root
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [pods]
  validations:
    - expression: >-
        object.spec.containers.all(c,
          c.?securityContext.?runAsNonRoot.orValue(false) == true)
      message: every container must set securityContext.runAsNonRoot to true

A ValidatingPolicy is cluster-wide; a NamespacedValidatingPolicy with the same fields applies only inside its own namespace, so a team can own its rules without cluster-admin rights. matchConstraints says which requests the policy wants, in the API server's own terms: the API group ("" is the core group that Pods live in), the version, the operations, and the resource's plural, lowercase name. validations is a list of CEL expressions, each of which must be true. object is the resource in the request. c.?securityContext is CEL's optional field access, which gives "no value" instead of an error when the field is missing, and orValue(false) supplies the value to use in that case. Run it:

kyverno apply policies/run-as-non-root.yaml --resource pods.yaml
echo $?
Applying 1 policy rule(s) to 5 resource(s)...
policy run-as-non-root -> resource shop/Pod/root failed:
1 -  every container must set securityContext.runAsNonRoot to true
policy run-as-non-root -> resource shop/Pod/unset failed:
1 -  every container must set securityContext.runAsNonRoot to true
policy run-as-non-root -> resource shop/Pod/inherits failed:
1 -  every container must set securityContext.runAsNonRoot to true

pass: 2, fail: 3, warn: 0, error: 0, skip: 0
1

Each failing resource is named with the message, and the summary counts results: pass and fail are verdicts, error means the expression itself failed to evaluate, and skip means a condition or exception excluded the resource. The exit status is 1 because something failed, which is what makes the command usable as a gate in CI (continuous integration). Two of the five verdicts are wrong: inherits is compliant and failed, and init is not and passed.

4. The field that is not there

Start with the mistake that looks like a fix. If inherits fails because its container says nothing, it is tempting to treat "says nothing" as compliant:

sed 's/orValue(false)/orValue(true)/' policies/run-as-non-root.yaml > lenient.yaml
kyverno apply lenient.yaml --resource pods.yaml
Applying 1 policy rule(s) to 5 resource(s)...
policy run-as-non-root -> resource shop/Pod/root failed:
1 -  every container must set securityContext.runAsNonRoot to true

pass: 4, fail: 1, warn: 0, error: 0, skip: 0

inherits passes now, for the wrong reason, and so does unset, which may well run as root: a container that does not set runAsNonRoot runs as whatever user its image names, and many images name root. The default you give a missing field is the policy's verdict on everyone who forgot, so it belongs on the strict side. The right fix follows Kubernetes' own rule: use the container's value if it has one, otherwise the Pod's, otherwise fail. Then do the same for every kind of container a Pod can have. Replace policies/run-as-non-root.yaml with:

# policies/run-as-non-root.yaml: every container, with Pod-level inheritance
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: run-as-non-root
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [pods]
  variables:
    - name: containers
      expression: >-
        object.spec.containers +
        object.spec.?initContainers.orValue([]) +
        object.spec.?ephemeralContainers.orValue([])
    - name: podDefault
      expression: object.spec.?securityContext.?runAsNonRoot.orValue(false)
    - name: offenders
      expression: >-
        variables.containers.filter(c,
          c.?securityContext.?runAsNonRoot.orValue(variables.podDefault) != true)
  validations:
    - expression: size(variables.offenders) == 0
      messageExpression: >-
        'may run as root: ' + variables.offenders.map(c, c.name).join(', ')
kyverno apply policies/run-as-non-root.yaml --resource pods.yaml
Applying 1 policy rule(s) to 5 resource(s)...
policy run-as-non-root -> resource shop/Pod/root failed:
1 -  may run as root: app
policy run-as-non-root -> resource shop/Pod/unset failed:
1 -  may run as root: app
policy run-as-non-root -> resource shop/Pod/init failed:
1 -  may run as root: setup

pass: 2, fail: 3, warn: 0, error: 0, skip: 0

All five verdicts are right. variables are named CEL expressions that later expressions read as variables.name, which keeps the validation itself one short line. messageExpression builds the message with CEL, so the denial names the container to fix; a denial that says what to change saves a support ticket every time it fires. Kyverno's own Pod Security policies do the same container arithmetic, because a check on containers alone is the commonest way to miss an init container and every container that kubectl debug adds.

5. The match that never matches

resources wants the plural, lowercase name that the API server uses in URLs, which is the NAME column of kubectl api-resources. Write the kind instead and see what happens:

sed 's/resources: \[pods\]/resources: [Pods]/' policies/run-as-non-root.yaml > typo.yaml
kyverno apply typo.yaml --resource pods.yaml
echo $?
Applying 1 policy rule(s) to 5 resource(s)...

pass: 0, fail: 0, warn: 0, error: 0, skip: 0
0

Five resources, no verdicts, exit status 0. [pod], [Pod], apiGroups: [core] and apiVersions: [v1beta1] all do the same. Nothing in the run tells you the policy is dead, and a CI job that checks only the exit status goes green. --warn-no-pass turns "nothing passed" into a separate exit status:

kyverno apply typo.yaml --resource pods.yaml --warn-exit-code 3 --warn-no-pass
echo $?
Applying 1 policy rule(s) to 5 resource(s)...

pass: 0, fail: 0, warn: 0, error: 0, skip: 0
exit as no objects satisfied policy
3

That catches a run where nothing passes at all. It counts across the whole run, though: give kyverno apply a folder of policies in which one is dead and the others pass something, and it exits 0. Catching one dead policy among many needs a statement of what each policy should find, which is what kyverno test in step 11 is for.

Besides resourceRules, matchConstraints takes a namespaceSelector (namespace labels), an objectSelector (the resource's labels) and excludeResourceRules, and the policy can add matchConditions, CEL expressions that must all be true for the policy to apply. Scope with them sparingly: step 6 shows what one of them costs.

6. Autogen: one Pod policy, every Pod controller

Most Pods are created by a controller such as a Deployment. Run the policy against the lab's Deployment:

kyverno apply policies/run-as-non-root.yaml --resource deploy.yaml
Applying 1 policy rule(s) to 1 resource(s)...
policy run-as-non-root -> resource shop/Deployment/api failed:
1 -  may run as root: api

pass: 0, fail: 1, warn: 0, error: 0, skip: 0

The policy matches only Pods, yet it judged the Deployment. This is autogen: for a policy that matches Pods, Kyverno generates variants for DaemonSets, Deployments, ReplicaSets, StatefulSets, Jobs and CronJobs, rewriting object.spec to the Pod template's path in each. That is why the variables in step 4 still worked. Without autogen, the Deployment would be accepted and its ReplicaSet would then fail to create Pods, so kubectl apply would succeed and the trouble would show up later, as a rollout that never completes and a ReplicaFailure condition on the Deployment.

Autogen runs only when the match is exactly one rule for core v1 pods, with no objectSelector, no excludeResourceRules and no resourceNames. Suppose you widen the policy to cover the ephemeral containers that kubectl debug adds, which arrive as an update to the pods/ephemeralcontainers subresource. Save this as ephemeral.yaml:

# ephemeral.yaml: the same policy, also matching kubectl debug
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: run-as-non-root-wide
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [pods]
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [UPDATE]
        resources: [pods/ephemeralcontainers]
  variables:
    - name: containers
      expression: >-
        object.spec.containers +
        object.spec.?initContainers.orValue([]) +
        object.spec.?ephemeralContainers.orValue([])
    - name: podDefault
      expression: object.spec.?securityContext.?runAsNonRoot.orValue(false)
    - name: offenders
      expression: >-
        variables.containers.filter(c,
          c.?securityContext.?runAsNonRoot.orValue(variables.podDefault) != true)
  validations:
    - expression: size(variables.offenders) == 0
      messageExpression: >-
        'may run as root: ' + variables.offenders.map(c, c.name).join(', ')
kyverno apply ephemeral.yaml --resource deploy.yaml
Applying 1 policy rule(s) to 1 resource(s)...

pass: 0, fail: 0, warn: 0, error: 0, skip: 0

The second rule switched autogen off, and the Deployment is no longer judged at all. Two ways to keep coverage: keep each Pod policy's match to plain pods and put the ephemeral-container check in a policy of its own, or do what Kyverno's own Pod Security policies do and list every controller in resourceRules, finding the Pod spec with a variable. Either way, put the exemptions you will be asked for ("except the debug Pod") in a PolicyException, which leaves the match, and so autogen, alone.

7. Deny, Audit, Warn, and failing open

validationActions says what a failed check does in a cluster: Deny rejects the request, Audit admits it and records the failure in a report, and Warn admits it and sends the client a warning that kubectl prints. Audit and Warn can be combined. Left out, it is Deny. Now change it and watch what the CLI says:

sed 's/validationActions: \[Deny\]/validationActions: [Audit]/' policies/run-as-non-root.yaml > audit.yaml
kyverno apply audit.yaml --resource pods.yaml
echo $?
Applying 1 policy rule(s) to 5 resource(s)...
policy run-as-non-root -> resource shop/Pod/root failed:
1 -  may run as root: app
policy run-as-non-root -> resource shop/Pod/unset failed:
1 -  may run as root: app
policy run-as-non-root -> resource shop/Pod/init failed:
1 -  may run as root: setup

pass: 2, fail: 3, warn: 0, error: 0, skip: 0
1

Exactly the same output as the denying version. The CLI reports whether each resource passes the check, and has no notion of what a cluster would do with a failure. Its --audit-warn flag changes each failure's label to failed as audit warning, but in 1.19.2 it does that for every ValidatingPolicy, including ones set to Deny, and leaves the counts and the exit status as they were, so it cannot tell the two apart for you either. Whether a policy blocks is a line in its YAML, and the only place to check it is there.

The rest of what decides a policy's behavior in a cluster is settings that a run on your laptop never exercises. These are the defaults in Kyverno 1.19:

Setting Default, and what it means
validationActions [Deny]: a failed check rejects the request. A legacy ClusterPolicy defaults the other way, to Audit (step 12).
failurePolicy Fail: if Kyverno cannot answer, or the expression errors, the request is rejected. Ignore lets it through unchecked. A GeneratingPolicy always uses Ignore.
timeoutSeconds 10, set under webhookConfiguration: how long the API server waits for Kyverno (1 to 30 seconds) before the failure policy decides.
evaluation.admission.enabled true: the policy judges requests at admission.
evaluation.background.enabled true: the policy also judges existing resources in the background scan (step 8).

Two settings outside the policy matter as much. The admission controller's --forceFailurePolicyIgnore flag (Helm value features.forceFailurePolicyIgnore.enabled, off by default) turns every policy's failure policy into Ignore, so the cluster fails open whenever Kyverno is unavailable. And the default install excludes namespaces: its webhooks skip kube-system and Kyverno's own namespace, and its resource filters also skip kube-public, kube-node-lease and kinds such as Event, Node and ReplicaSet. A policy can match everything and still never be asked about a Pod in kube-system at admission. The background scan of step 8 does report on those namespaces, because by default it ignores the resource filters.

The exclusions exist for a reason. With failurePolicy: Fail and Kyverno down, every matching request is rejected, and if that included the system Pods that would bring Kyverno back, the cluster could not recover on its own. Kyverno's troubleshooting guide covers that case by deleting its webhook configurations so the API server stops calling it, and they are recreated when Kyverno comes back. The safe pattern is Fail plus at least three admission-controller replicas, with the exclusions left alone, rather than Ignore.

8. Existing resources, background scans and reports

Admission sees requests, so on the day you apply a new denying policy, nothing already running changes. Kyverno's answer for existing resources is the background scan: the reports controller re-checks matching resources periodically, every hour by default, and records the results. It never blocks or deletes anything, whatever validationActions says. Ask the CLI for the same kind of report:

kyverno apply policies/run-as-non-root.yaml --resource pods.yaml --policy-report

After the usual summary it prints a report with one entry per verdict. The first is:

apiVersion: openreports.io/v1alpha1

  name: merged

- message: 'may run as root: app'

In a cluster, Kyverno 1.19 writes these by default as PolicyReport objects (one per namespaced resource, in its namespace) and ClusterPolicyReport objects (for cluster-scoped resources), in the wgpolicyk8s.io/v1alpha2 API group; the openreports.io format the CLI prints is an alpha alternative you can switch the cluster to. Either way, a report is where you find out what a new policy would break before you let it deny anything, and where you find the resources it never will.

Results from admission also land in reports, including for Audit, which is the point of Audit. Set evaluation.background.enabled: false only for a policy that reads something that exists only in an admission request, such as who made it.

9. Mutate and generate

A MutatingPolicy changes the resource on its way in. This one gives every new Pod that does not set one the RuntimeDefault seccomp profile, the container runtime's standard filter on which system calls a container may make. Save it as default-seccomp.yaml:

# default-seccomp.yaml: give Pods the RuntimeDefault seccomp profile if they set none
apiVersion: policies.kyverno.io/v1
kind: MutatingPolicy
metadata:
  name: default-seccomp
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE]
        resources: [pods]
  matchConditions:
    - name: no-seccomp-profile-yet
      expression: >-
        !has(object.spec.securityContext) ||
        !has(object.spec.securityContext.seccompProfile)
  mutations:
    - patchType: ApplyConfiguration
      applyConfiguration:
        expression: >-
          Object{
            spec: Object.spec{
              securityContext: Object.spec.securityContext{
                seccompProfile: Object.spec.securityContext.seccompProfile{
                  type: "RuntimeDefault"
                }
              }
            }
          }
kyverno apply default-seccomp.yaml --resource pods.yaml

10. Verify image signatures

An ImageValidatingPolicy checks container images rather than resource fields: who signed them, and what attestations (signed statements about how an image was built, such as an SBOM (software bill of materials) or provenance) they carry. It works with Sigstore's cosign signatures and with Notary. Kubernetes signs its own release images with Sigstore's "keyless" signing, which ties each signature to an OpenID Connect identity rather than a long-lived key, so its images make a real test. This step reaches the network: it reads signatures from registry.k8s.io and checks them against Sigstore's public services. Save signed-images.yaml and images.yaml:

# signed-images.yaml: images from registry.k8s.io must be signed by the Kubernetes release team
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: k8s-images-signed
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE]
        resources: [pods]
  matchImageReferences:
    - glob: "registry.k8s.io/*"
  attestors:
    - name: k8s
      cosign:
        keyless:
          identities:
            - issuer: https://accounts.google.com
              subject: krel-trust@k8s-releng-prod.iam.gserviceaccount.com
  validations:
    - expression: >-
        images.containers.map(image,
          verifyImageSignatures(image, [attestors.k8s])).all(n, n > 0)
      message: registry.k8s.io images must be signed by the Kubernetes release team
# images.yaml: one image the policy covers and one it does not

Here is the check from step 4 written the pre-1.19 way, plus a second rule that denies privileged containers. Save legacy.yaml, and privileged.yaml for the second rule to catch:

# legacy.yaml: two rules in the kyverno.io/v1 format that 1.20 stops running
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: legacy-pod-rules
spec:
  rules:
    - name: run-as-non-root
      match:
        any:
          - resources:
              kinds: [Pod]
      exclude:
        any:
          - resources:
              namespaces: [kube-system]
      validate:
        message: every container must set securityContext.runAsNonRoot to true

          spec:
            containers:
              - =(securityContext):

        any:

Read it from the top. A ClusterPolicy applies cluster-wide and a Policy only in its own namespace. Each rule has a match and an optional exclude, each with any (at least one entry must apply) or all (every entry must), and each entry filters on kinds, names, namespaces, label selectors, or who made the request. Kinds are written as kinds, Pod, optionally as group/version/Kind; misspell one and the CLI reports zeros, just as in step 5. "6 policy rule(s)" is two rules plus autogen's variants, which a legacy policy gets for Pod rules by default.

pattern is an overlay: the resource must look like the YAML under it, and a plain field in the pattern must exist in the resource. Values can be wildcards (?* means "any non-empty value") or comparisons (>3, !*:latest). Anchors change what a field means:

  • =(field), equality: if the field is present, it must match. If it is absent, the check passes.
  • (field), conditional: if this matches, check the rest of the pattern; if it does not, skip.
  • ^(field), existence: at least one element of the list must match.
  • X(field), negation: the field must not be present.
  • <(field), global: if this does not match, skip the whole rule.
  • +(field), add if not present, which appears in mutate rules.

Look at the results with that in mind. unset and init passed. Both =() anchors are equality anchors, so a container with no securityContext satisfies the pattern, which is exactly the lenient default of step 4 in another syntax. Remove the anchors and unset fails, but so does inherits, and the pattern still sees only containers.

deny is the other way to validate: the request is denied when the conditions hold. The {{ }} are variables, written in JMESPath, a query language for JSON (JavaScript Object Notation) that is also built into the AWS CLI, and that the jq and JMESPath guide teaches. request.object is the resource; containers[?securityContext.privileged == `true`] is a filter projection keeping the privileged containers, and | length(@) counts them. The backticks around true make it a JSON literal, and exercise 3 shows what happens with quotes instead. In CEL the whole rule is one expression, !object.spec.containers.exists(c, c.?securityContext.?privileged.orValue(false)), with the logic turned around because a deny condition says what is forbidden and a validation says what must be true.

Now check the enforcement mode. Neither rule sets failureAction, so both fall back to the policy-wide default, and --audit-warn shows what that is:

kyverno apply legacy.yaml --resource pods.yaml --resource privileged.yaml --audit-warn
echo $?
pass: 10, fail: 0, warn: 2, error: 0, skip: 0
0

The two failures became warnings and the exit status 0: both rules are in Audit mode. A legacy policy blocks only where a rule says failureAction: Enforce, the deprecated policy-wide validationFailureAction says Enforce, or a per-namespace override (failureActionOverrides) does, so a policy written to block that never says so only ever reports. For a legacy policy that is in one mode throughout, --audit-warn does show the difference, unlike for the new types: with Enforce the failures stay failures. Legacy validate rules also default to allowExistingViolations: true, which lets an update through to a resource that already violated the rule before the update.

To migrate, Kyverno's migration guide maps every field. The ones that matter most:

Legacy ClusterPolicy Current types
One policy, many rules of different kinds One policy type per action: ValidatingPolicy, MutatingPolicy, GeneratingPolicy, ImageValidatingPolicy, DeletingPolicy
match on kinds; exclude matchConstraints.resourceRules on group, version and plural resource; excludeResourceRules; matchConditions
pattern, anyPattern, foreach CEL in validations, using all(), exists() and optional fields
deny conditions CEL in validations, with the logic inverted
context and JMESPath variables variables, plus Kyverno's CEL libraries for lookups and API calls
failureAction, default Audit validationActions, default Deny
allowExistingViolations, failureActionOverrides Not supported; Kyverno points to PolicyExceptions instead

The default in the last row but one is the trap: a legacy policy that was quietly auditing becomes, translated field for field, a policy that denies. Decide which you want and write it down in validationActions. Then run the old and new policies side by side with the CLI against the same resources, as this step and step 4 did, before deleting anything. Kyverno's documentation also describes --warnings-as-errors and the kyverno_deprecated_api_requests_total metric for finding legacy policies that are still in use.

sed "s/privileged == \`true\`/privileged == 'true'/" legacy.yaml > legacy-quoted.yaml

Applying 6 policy rule(s) to 1 resource(s)...

pass: 2, fail: 0, warn: 0, error: 0, skip: 0

debug passes both rules. In JMESPath, single quotes make a string, so the filter compares the boolean true in the Pod with the string "true", finds no match, and the count is 0. The rule still loads, still runs, and denies nothing. The jq and JMESPath guide has the same trap in its JMESPath step. CEL does not protect you from the same slip. Kyverno reads a Pod's fields as dynamic values, so c.?securityContext.?privileged.orValue(false) == 'true' is quietly false for every container too; CEL rejects the comparison only when it can see both types before it runs. Drop the comparison and use the boolean itself:

# no-privileged.yaml: the legacy deny rule as a ValidatingPolicy
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: no-privileged
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [pods]
  validations:
    - expression: >-
        !object.spec.containers.exists(c,
          c.?securityContext.?privileged.orValue(false))
      messageExpression: >-
        'privileged containers: ' + object.spec.containers
          .filter(c, c.?securityContext.?privileged.orValue(false))
          .map(c, c.name).join(', ')
kyverno apply no-privileged.yaml --resource privileged.yaml --resource pods.yaml
Applying 1 policy rule(s) to 6 resource(s)...
policy no-privileged -> resource shop/Pod/debug failed:
1 -  privileged containers: shell

pass: 5, fail: 1, warn: 0, error: 0, skip: 0

Here orValue(false) is the right default: a container that does not ask for privileged mode does not get it.

Common mistakes

  • Writing a new ClusterPolicy. 1.19 is the last release that runs them. Anything you write today should be one of the policies.kyverno.io/v1 types.
  • Trusting a green kyverno apply. A policy that matches nothing exits 0. Give every policy a kyverno test file with results both ways, and run it with --require-tests.
  • Leaving the action to the default. Legacy rules default to Audit, the current types to Deny, and the CLI reports a failure either way. Write validationActions in every policy.
  • Defaulting a missing field to compliant. orValue(true) and the =() anchor both pass a container that never set the field. Default to the strict value unless absence is safe, as it is for privileged.
  • Checking containers only. Init and ephemeral containers run too. Join the three lists, as in step 4.
  • Putting exemptions in the match. An excludeResourceRules entry, an objectSelector or a second resource rule on a Pod policy switches autogen off, and the Deployments stop being judged. Use a PolicyException, and remember that exceptions do nothing until enabled: the Helm chart ships with features.policyExceptions.enabled set to false. When you turn it on, set features.policyExceptions.namespace too, because left empty, Kyverno honors exceptions from every namespace, and anyone who can create one anywhere can exempt their own workloads. The CLI applies any exception you hand it, so it can disagree with the cluster.
  • Assuming system namespaces are covered. The default install never sends Kyverno a request from kube-system, and filters several other namespaces and kinds. Cover them another way, or change the exclusions knowing why they are there.
  • Fixing availability with Ignore. failurePolicy: Ignore, or --forceFailurePolicyIgnore on the admission controller, means every outage of Kyverno is an outage of your policy too. Run more replicas instead.
  • Expecting a new policy to clean up. Denying policies leave existing resources running. Read the background scan's reports, then fix or redeploy what they list.
  • Scoping an image policy to one registry and stopping there. An image outside matchImageReferences passes unchecked. Pair it with a rule that allows only registries you trust.
